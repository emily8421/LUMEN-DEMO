# TEMPLATE-UPGRADE: 文档体系周期性健康度复核机制（防臃肿 / 可读性维护）

> 来源：LUMEN（emily8421/LUMEN-DEMO）派生项目回流

## 1. 背景与问题

模板的文档演进采用「积累式」（`ai/global-rules.md` §8：只增不删、原位演进）。这套机制保证了历史可追溯，但也带来一个真实副作用：**文档在一轮轮「分析-设计-实现-回流」中持续变厚，缺少周期性整理 / 瘦身 / 可读性维护的常态机制**。

现有文档评审能力盘点：

| 机制 | 触发时机 | 侧重 | 是否覆盖「臃肿 / 可读性 / 周期维护」 |
|---|---|---|---|
| `docs-evaluation` | 阶段转换（E1-E6） | 完整性 / 可行性 / 一致性，Go / No Go | 部分（「维护性」维度偏结构化，非专门查臃肿） |
| `docs-system-audit` | 项目成型 / 同步后 | 全链路追溯、规范基线缺口 | 部分（含 H2/H3 编号统一检查，但偏追溯一致性） |
| `docs-checklist` | 编码前 | 阶段边界 / 验证闭环 | 否 |
| `docs-open-items` | 待确认项累积 | 防悬空 ID | 否（配套机制） |
| `post-sync-cleanup` | 模板同步后 | 分区 / README / project-rules | 否 |
| `sync-docs-from-code` | 代码事实漂移 | 文档滞后回写 | 否（解决滞后，非臃肿） |

**缺口**：以上全部是「阶段触发 / 一次性」，没有「周期性 / 收尾触发的文档健康度检查」——即「这轮工作收尾时，顺手对文档体系的臃肿、重复、可读性、过时残留做一次梳理」的常态机制。同时，`global-rules §8` 的「只增不删」没有配套的「允许在保留可追溯前提下整理 / 瘦身」的明确通道，导致 AI 对「看起来冗余」的内容不敢动，臃肿只能单向累积。

## 2. 实证：LUMEN 当前文档体系的健康度问题（2026-08-08 体检）

用现有机制对 LUMEN docs 做了实际扫描，确认问题真实存在：

1. **超长头部元信息（可读性退化）**：`docs/08-dev-plan.md` 与 `docs/09-verification.md` 的「当前状态」元信息是把 5 个阶段（Phase1 → Phase2D）的完成情况全部堆在**单个表格单元格**里的超长段落（08 头 1 段 ≈ 400+ 字，09 头 1 段 ≈ 500+ 字）。积累式演进把「该阶段一句话状态」膨胀成「历史全量叙述」，读者难快速抓住「当前在哪里、下一步做什么」。
2. **过时状态残留（内容滞后）**：`docs/08-dev-plan.md:55` Sprint-30 仍标「**编码完成待提交** / 提交 + bump v3.3.0 待执行」，但该 Sprint 早已提交并推送（`59dd898`）；`08:76` Sprint-23A 仍标「**已编码 PR #104，待合并**」，而 Sprint-24/25 早已完成。这些「过程性状态」未随完成而推进。
3. **已解决项累积（信息结构退化）**：`docs/09-verification.md` §6 风险表用删除线保留 8 处「已解决」项 + 10 处「已解决」标注并存，读者难快速分辨「当前风险」与「历史已解决」。
4. **待办 / 待确认标记分布广**：33 处「待办 / 未回写 / 历史遗留 / 待人工确认」等标记散布在 23 个文档中——多数是正式待确认项（合理），但确实存在「完成未推进状态」与「机制性待确认」混在一起、无法一眼区分的问题。

这些问题的共同根因是：**积累式演进保证了可追溯，但没有配套的周期性健康度检查来识别「过时状态未推进、信息结构退化、可读性下降」**。

## 3. 建议修改

在模板中新增**轻量「文档健康度复核」机制**，作为现有命令体系的补位，不替换任何现有命令：

### 3.1 新增命令 `docs-health-review`（或作为 `docs-system-audit` 的轻量模式）

- **用户说法**：`/run docs-health-review` / 文档健康度检查 / 收尾梳理文档 / 文档瘦身 / 检查文档可读性
- **触发时机**：周期性（如每 Sprint / Phase 收口时），或用户主动要求——与现有「阶段触发」命令互补。
- **检查维度**（四类信号，区别于 docs-system-audit 的追溯 / 规范维度）：
  1. **内容重复**：同一事实 / 结论在多处重述，未引用权威源。
  2. **章节臃肿**：单章 / 单段异常超长（如超长头部元信息），信息密度失衡。
  3. **结构退化**：标题层级混乱、编号跳号重复、过时过程性段落残留。
  4. **状态滞后**：已完成事项仍标「待提交 / 待合并 / 待验收 / 待实现 / 待设计细化」等过程状态，已解决项与当前风险混排。
  5. **状态交叉核对（操作化）**：主动对照**权威状态源**（`ai/project-rules.md` §1 Phase 指针、`docs/03-prd.md` §3 路线图、`docs/09-verification.md` §5 验收证据），逐文档核对其中的 REQ / Phase / API / 功能状态标记是否与权威源同步。实证：2026-08-08 体检发现 7 处「实现已完成但状态标记未推进」（如 `02` 的 REQ-045/046/047 标「待实现」、`04` REQ-013/014 标「待设计」、`05` Phase2B「未切指针」，权威源均已标完成）——此类残留靠人工逐文档比对才能发现，正是该维度要自动化捕获的。
- **输出**：区分「**可安全整理**」（纯过程性残留，如已完成的「待提交」标记）与「**需人工确认**」（涉及历史事实 / 追溯锚点 / 阶段结论）两类清单，每项给出 `文件:行`、类型、严重度、建议处理方式。
- **默认只读**，不直接改文件；整理需另行确认。

### 3.2 明确「只增不删」的整理例外通道

在 `ai/global-rules.md` §8 补充「**整理（tidy）例外**」：

- **允许**：删除 / 合并**已过时的过程性记录**（如已完成但未推进的状态标记、不再指向当前事实的临时描述）、将超长头部元信息重构为「当前状态 + 历史指针」结构、把过时过程段落移入 `docs/archive/`。
- **禁止**：删除 / 改写**历史事实与追溯锚点**（REQ / 设计结论 / 验收记录 / 决策记录）。历史事实进 archive 或留一行指针，保持 global-rules §8 的可追溯底线。
- **判断准则**：整理后仍能从当前文档追溯到全部历史事实；不确定时标「需人工确认」。

### 3.3 触发点接入

- 在 `ai/session-rules.md` §4（自动更新触发点）或 §3.3（Checkpoint Mode）补一条：**完成一个 Sprint / Phase 收口、或连续多轮文档修改后，可运行 `docs-health-review` 做一次收尾梳理**。
- 在 `template-docs/scenario-guides.md` 增加「文档健康度复核」场景（可并入 A7 PLM 转换或收尾场景）。

## 4. 去项目化边界

- 本提案只描述「通用机制缺口 + 检查维度 + 整理例外」，不涉及 LUMEN 具体文档内容、路径或业务细节。
- 实证中的 LUMEN 文档位置仅用于说明问题形态，不进入模板。

## 5. 版本影响与兼容性

- **版本影响**：模板 minor（新增命令 / 场景 / 规则补充，不破坏既有命令）。
- **兼容性**：现有 `docs-system-audit` / `docs-evaluation` / `docs-checklist` 不变；新增命令默认只读；`global-rules §8` 例外通道是「允许」而非「强制」，既有文档无需迁移。

## 6. 验收标准

模板落地后应满足：

1. 用户说「收尾梳理文档」或「检查文档可读性」，AI 能路由到 `docs-health-review`。
2. 该命令能识别「已完成但状态滞后」「超长章节」「重复内容」「结构退化」四类信号并输出 `文件:行` 定位。
3. 输出区分「可安全整理」与「需人工确认」，默认只读不直接改文件。
4. `global-rules §8` 有明确的「整理例外」通道：允许清理过时过程性记录，但历史事实 / 追溯锚点保留或进 archive。
5. 与现有命令不冲突；`docs-system-audit` 仍可做全链路回溯。
