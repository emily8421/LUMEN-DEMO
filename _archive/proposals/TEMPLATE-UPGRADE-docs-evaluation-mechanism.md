# TEMPLATE-UPGRADE: 文档评估机制

> 来源：LUMEN_demo_T2.1（emily8421/LUMEN-DEMO）派生项目回流

## 1. 背景与问题

当前模板已经有文档生成、文档检查、项目审查和文档体系全链路审计能力，但缺少一种“正式评估机制”：

- 审计偏发现问题，默认只读输出，不定义评估报告如何沉淀为项目事实留痕。
- 编码前检查偏当前开发就绪，不覆盖愿景、需求、设计之间的阶段转换质量。
- 单文档修改有 Prompt，但缺少单个文档在输入、职责、追溯、下游影响上的独立评估入口。
- 派生项目在文档体系成型后，常需要留下“为什么认为当前文档可以进入下一阶段”的评估证据。

因此建议在模板中新增“文档评估机制”，用于在关键阶段转换前后生成可落盘、可追踪、可复评的评估报告。

## 2. 目标

新增机制应满足：

1. 支持整体评估、阶段评估、单文档评估三种粒度。
2. 明确评估规则：完整性、合理性、可行性、一致性、追溯性、阶段边界、风险与待确认项。
3. 明确报告生成机制：默认先只读评估，用户确认后落盘到标准目录。
4. 与现有 `docs-system-audit` 区分：审计用于全链路回溯发现问题，评估用于形成阶段判断与正式留痕。
5. 补充命令路由、Prompt 和场景指引，使用户能用自然语言触发。

## 3. 评估类型

### 3.1 整体评估

适用于项目文档体系已基本成型，需要判断当前文档体系是否能支撑下一阶段。

评估内容：

- 文档链是否完整：输入、00-09、design/env/research 等是否按项目形态存在。
- 追溯链是否完整：输入来源 → U-ID → REQ-ID → Phase → 设计 → 计划 → 验证。
- 阶段边界是否清楚：愿景、当前阶段、后续阶段是否分离。
- 横切事实是否一致：技术栈、资源、权限、合规、Mock / 降级策略是否有权威源。
- 风险是否显式：高风险能力是否被标为待验证或后续阶段。
- 是否可进入下一阶段：给出 Go / Conditional Go / No Go 结论。

### 3.2 阶段评估

适用于两个 PLM 阶段之间的转换判断。

建议内置阶段：

| 评估码 | 阶段转换 | 核心问题 |
|---|---|---|
| E1 | 输入 / 愿景 → 需求阶段 | 输入是否足以生成 00-03；是否有来源锚点与需求编号 |
| E2 | 需求阶段 → 总体设计 | 04-05 是否只承接已授权需求；架构和技术基线是否可行 |
| E3 | 总体设计 → 详细设计 | 06/07/design 是否覆盖关键模块、数据、接口和流程 |
| E4 | 详细设计 → 实现计划 | Sprint 是否可执行、粒度是否合适、禁止事项是否明确 |
| E5 | 实现计划 → 验证 | 09 是否覆盖 REQ 与 Sprint 验收，Mock / 降级边界是否明确 |
| E6 | 实现结果 → 文档回写 | 代码事实是否需要反向同步到 docs |

阶段评估输出应包含：转换结论、合规项、问题项、风险项、修复建议、是否阻塞下一阶段。

### 3.3 单文档评估

适用于修改或评审某一份核心文档前后。

评估内容：

- 输入来源是否明确。
- 输出职责是否符合文档定位。
- 是否引入上游未授权内容。
- 追溯 ID 是否完整且无悬空。
- 阶段标签、交付物形态、状态是否一致。
- 待人工确认项是否真实，不用“无”掩盖风险。
- 下游影响是否列明。

## 4. 评估规则

建议在 Prompt 中固定以下评估维度：

| 维度 | 判断问题 | 输出要求 |
|---|---|---|
| 完整性 | 必需文档、章节、矩阵、图表是否存在 | 列缺失项和影响 |
| 合理性 | 需求拆分、阶段归属、优先级是否符合项目目标 | 说明是否需要重分层 |
| 可行性 | 技术、资源、数据、Mock / 降级是否支撑目标 | 给出风险和验证建议 |
| 一致性 | 横切事实是否冲突或重复定义 | 指定权威源和残留位置 |
| 追溯性 | 是否能从输入追到需求、设计、计划、验证 | 列断点和悬空 ID |
| 阶段边界 | 当前阶段是否混入后续功能 | 标出越界内容 |
| 可验证性 | 需求和设计是否有可验收口径 | 标出不可测条目 |
| 维护性 | 文档是否便于后续增量演进 | 标出结构化改进项 |

评估结论建议使用：

- `Go`：可进入下一阶段，无阻塞项。
- `Conditional Go`：可进入下一阶段，但需先处理列出的 P0 / P1 项。
- `No Go`：存在关键断点或范围冲突，不应进入下一阶段。

问题优先级建议使用：

- `P0`：阻塞当前阶段或下一阶段入口。
- `P1`：不阻塞，但应在相关 Sprint / Phase 前处理。
- `P2`：后续优化或升阶段时处理。

## 5. 报告生成机制

### 5.1 默认流程

1. 读取 `ai/index.md` 及其列出的规则文件。
2. 根据用户意图判断评估粒度：整体、阶段、单文档。
3. 只读扫描相关 docs、doc-standards、project-rules、env、design 文档。
4. 先在对话中输出评估报告草稿。
5. 用户确认需要记录后，将报告写入 `docs/research/`。
6. 若评估发现模板通用缺口，可同步起草 `_proposals/TEMPLATE-UPGRADE-*.md`。

### 5.2 推荐报告路径

```text
docs/research/YYYY-MM-DD-docs-evaluation-<scope>.md
```

示例：

```text
docs/research/2026-07-03-docs-evaluation-vision-to-design.md
docs/research/2026-07-03-docs-evaluation-single-03-prd.md
docs/research/2026-07-03-docs-evaluation-full-chain.md
```

理由：评估报告属于分析和判断留痕，不应放在 docs 根目录；也不应默认放入 archive，因为它可能驱动后续回梳。

### 5.3 报告结构

```markdown
# 文档评估报告：<scope>

## 1. 评估摘要
## 2. 评估范围与依据
## 3. 整体评估 / 阶段评估 / 单文档评估
## 4. 合规项
## 5. 问题项
## 6. 风险项
## 7. 修复建议
## 8. 是否阻塞下一阶段
## 9. 待人工确认项
```

## 6. 命令与 Prompt 建议

### 6.1 新增命令

建议新增：

```text
ai/commands/docs-evaluation.md
```

命令别名 / 用户说法：

- `/run docs-evaluation`
- 文档评估
- 阶段文档评估
- 单文档评估
- 评估愿景到需求
- 评估需求到设计

命令职责：

- 识别评估粒度和范围。
- 默认只读输出评估草稿。
- 用户明确要求“记录下来 / 落盘 / 形成报告”时，写入 `docs/research/`。
- 不直接修复 00-09；修复应转交 `edit-single-doc` 或对应文档生成 / 回梳 Prompt。

### 6.2 新增 Prompt

建议新增：

```text
ai/prompts/review/19-docs-evaluation.md
```

Prompt 应包含：

- 三种评估粒度选择规则。
- 阶段评估码 E1-E6。
- 固定评估维度和结论等级。
- 报告落盘路径规则。
- 与 `docs-system-audit`、`docs-checklist`、`project-review` 的区别。

### 6.3 与现有命令关系

| 命令 | 定位 | 与 docs-evaluation 的区别 |
|---|---|---|
| `docs-checklist` | 开发前验收 | 更偏当前任务是否可开工 |
| `docs-system-audit` | 全链路回溯审计 | 更偏发现问题，默认不落盘 |
| `project-review` | 实现合规审查 | 更偏代码 / 实现是否符合 docs |
| `edit-single-doc` | 修改单个文档 | 评估后确认修复时使用 |
| `docs-evaluation` | 正式文档评估 | 可分粒度、可落盘、给阶段判断 |

## 7. 场景补充建议

建议在 `template-docs/scenario-guides.md` 增加“文档评估”场景，可作为 A7 PLM 转换的横切检查，或放入 A11/A13 附近作为项目文档健康评估入口。

推荐场景：

| 场景码 | 场景 | 触发语 | 产出 |
|---|---|---|---|
| A7.E | PLM 阶段评估 | “评估愿景到需求 / 需求到设计” | 阶段评估报告 |
| A11.E | 开发前文档评估 | “编码前先评估文档是否够用” | Go / Conditional Go / No Go |
| A13.E | 同步后文档评估 | “模板同步后重新评估文档体系” | 同步后差异评估报告 |

场景步骤：

1. 判断评估粒度和范围。
2. 只读扫描相关文档。
3. 输出评估草稿。
4. 若用户要求落盘，写入 `docs/research/`。
5. 若发现通用模板缺口，建议起草 `_proposals/TEMPLATE-UPGRADE-*.md`。

## 8. 与现有 docs-system-audit 的关系

建议保留 `docs-system-audit`，不替换。

- `docs-system-audit`：适合项目已成型后做全链路回溯，偏“审计 / 找问题 / 回梳计划”。
- `docs-evaluation`：适合阶段推进、单文档评审、正式留痕，偏“评估 / 判断 / 报告记录”。

两者可共享部分评估维度，但输出语义不同：

- 审计输出：健康度总览、断点、残留、回梳计划。
- 评估输出：Go / Conditional Go / No Go、问题优先级、是否阻塞下一阶段、报告落盘。

## 9. 版本影响与兼容性

建议版本影响：minor。

原因：

- 新增命令、Prompt、场景和报告模板，不破坏既有命令。
- 派生项目无需迁移既有文档。
- 已有 `docs/research/` 分区规则可承接评估报告。
- 若派生项目没有 `docs/research/`，执行时创建目录即可。

兼容策略：

- 旧项目仍可继续使用 `docs-system-audit`。
- 新命令默认只读，不会自动修改 00-09。
- 报告落盘需要用户明确提出“记录 / 落盘 / 形成报告”。

## 10. 验收标准

模板落地后应满足：

1. 用户输入“评估愿景到需求阶段文档”，AI 能路由到 `docs-evaluation`。
2. 用户输入“评估需求到总体设计”，AI 能输出阶段评估并给 Go / Conditional Go / No Go。
3. 用户输入“评估单个 03-prd”，AI 能只读检查该文档的输入、职责、追溯、阶段边界和下游影响。
4. 用户要求“记录下来”时，AI 能写入 `docs/research/YYYY-MM-DD-docs-evaluation-<scope>.md`。
5. 评估报告不进入 docs 根目录，不覆盖 00-09，不替代正式修订。
6. 若发现模板通用问题，AI 能建议起草 `_proposals/TEMPLATE-UPGRADE-*.md`。
