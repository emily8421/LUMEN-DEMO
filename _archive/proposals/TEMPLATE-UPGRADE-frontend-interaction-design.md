# TEMPLATE-UPGRADE: 前端交互设计文档规则

> 来源：LUMEN_demo_T2.1（emily8421/LUMEN-DEMO）派生项目回流

## 1. 背景与问题

当前模板已经规定：

- `docs/04-architecture.md` / `docs/05-tech-spec.md` 承载前端架构与技术栈。
- `docs/design/` 承载非平凡子系统 / 模块详细设计。
- 独立 Web / 移动端演示形态应保留 `frontend/` 并在架构与技术方案中体现。

但模板尚未明确：当项目存在真实前端交互时，是否需要一份独立的 UI / 交互详细设计文档，以及这份文档应放在哪里、覆盖什么、如何与 00-09 追溯。

派生项目在进入前端相关 Sprint 前容易出现以下问题：

- 需求、API、验证中已有前端相关约束，但页面结构和用户流散落在多个文档中。
- 各 Sprint 分别生成页面，容易出现导航、空态、错误态、权限可见性不一致。
- 前端实现可能把“隐藏入口”误当作权限边界，弱化后端权限过滤原则。
- UI 设计若放入 docs 根目录，容易破坏 `00-09` 固定编号体系。

因此建议模板增加“前端交互设计文档”的条件性规则。

## 2. 目标

新增规则应满足：

1. 明确何时建议新增前端交互设计文档。
2. 明确推荐路径为 `docs/design/frontend-interaction.md`，不得新增 `docs/10-ui-design.md` 等根目录编号外文档。
3. 明确文档只细化既有需求的界面呈现，不得绕过 `00-09` 新增功能。
4. 明确 UI 文档应覆盖页面结构、核心用户流、状态反馈、权限可见性、适配范围和验收追溯。
5. 明确若 UI 设计引入新需求、接口、验收标准或权限行为，必须反向同步对应 `03/04/07/08/09`。

## 3. 建议新增规则

### 3.1 触发条件

当项目满足以下任一条件时，建议新增前端交互设计文档：

- `ai/project-rules.md` §3 保留 `frontend/`，且项目交付物包含独立 Web、桌面端、移动端或多页面交互。
- `docs/08-dev-plan.md` 的 Sprint 修改范围包含前端页面、组件、编辑器、搜索 / 问答 UI、管理页或桌面端集成。
- 验收依赖用户在界面中完成多步操作，如登录、空间切换、导入、搜索、问答、编辑、审批或管理配置。
- 项目存在多角色、多权限、多状态、复杂空态 / 错误态，前端呈现会影响验收一致性。

若项目只是 CLI、脚本、消息通道内交互或单一极简页面，则不强制新增该文档。

### 3.2 推荐路径

```text
docs/design/frontend-interaction.md
```

可接受别名：

```text
docs/design/ui-interaction.md
docs/design/frontend-ui.md
```

不建议路径：

```text
docs/10-ui-design.md
docs/ui-design.md
docs/design-ui.md
```

理由：UI / 交互设计属于详细设计，应进入 `docs/design/`；`docs/` 根目录继续只保留 `README.md` 与 `00-09` 核心文档。

### 3.3 推荐文档结构

```markdown
# 详细设计：前端交互与界面（frontend-interaction）

> 本文承接 03/04/05/07/08/09，只定义既有需求的界面呈现，不新增需求、接口或验收目标。

## 1. 职责与边界
## 2. 页面信息架构
## 3. 页面清单与 REQ 追溯
## 4. 核心用户流
## 5. 状态、空态与错误态
## 6. 权限与可见性原则
## 7. 适配范围（桌面 / 移动 / 可访问性，按项目需要）
## 8. 与 API / Sprint / 验证追溯
## 9. 阶段增量
## 10. 待人工确认项
```

### 3.4 内容边界

文档应写：

- 页面 / 视图 / 导航结构。
- 关键用户流和交互步骤。
- 加载态、空态、错误态、禁用态。
- 权限可见性与安全边界说明。
- 与 API、Sprint、验收用例的追溯矩阵。
- 当前阶段与后续阶段差异。

文档不应写：

- 上游未授权的新功能。
- 未定义接口的请求 / 响应契约。
- 过早锁定的视觉品牌、精细 UI 稿或具体组件库，除非项目技术方案已批准。
- 把前端隐藏、按钮禁用或路由守卫写成唯一权限边界。

## 4. 与现有 00-09 的关系

前端交互设计文档不替代 `00-09`，只作为详细设计补充：

| 关系 | 规则 |
|---|---|
| 与 `03-prd.md` | 只能承接已批准 REQ 与阶段范围 |
| 与 `04-architecture.md` | 承接前端架构、子系统划分和安全边界 |
| 与 `05-tech-spec.md` | 承接前端技术栈、运行环境和依赖边界 |
| 与 `07-api-spec.md` | 只能调用已定义接口；新增接口需先同步 API 文档 |
| 与 `08-dev-plan.md` | 支撑前端相关 Sprint 拆分和修改范围 |
| 与 `09-verification.md` | 将界面操作映射到验收用例 |

若 UI 文档发现 00-09 缺口，应先列为待确认项，不得直接在 UI 文档中“补写事实”。

## 5. 命令与 Prompt 建议

### 5.1 文档生成 Prompt

建议在现有文档生成 / 单文档编辑 Prompt 中增加判断：

- 若项目保留 `frontend/` 且存在多页面或验收依赖 UI，提示用户是否新增 `docs/design/frontend-interaction.md`。
- 生成前必须读取 `03/04/05/07/08/09` 与相关 `docs/design/*`。
- 输出生成前声明：输入文档、约束文档、允许修改范围、不得新增内容、下游影响。

### 5.2 文档检查 / 审计 Prompt

建议在 `docs-checklist`、`docs-system-audit`、`project-review` 中增加检查项：

- 项目若有前端 Sprint，是否存在 UI / 交互设计依据。
- 页面、状态、权限可见性是否与 API / 验证矩阵一致。
- 前端是否被误写成权限安全边界。
- UI 文档是否没有越权新增需求、接口或验收目标。

### 5.3 场景引导

建议在场景指引中补充触发语：

- “补前端交互设计”
- “开始前端 Sprint 前先整理页面设计”
- “把页面结构和用户流写成详细设计”
- “检查项目是否缺 UI 设计文档”

## 6. 版本影响与兼容性

建议版本影响：minor。

原因：

- 只新增条件性建议和文档模板，不破坏既有 `00-09` 编号体系。
- 已有项目无需迁移；只有存在前端交互复杂度时才建议新增。
- 文档路径落在既有 `docs/design/` 分区，兼容当前目录规范。

兼容策略：

- CLI / 脚本 / 消息通道项目可不新增 UI 文档。
- 已有 UI 设计文档可保持原名，但建议后续归并到 `docs/design/`。
- 若项目已在 `04/05/08/09` 中充分覆盖简单页面，可只在审计中记录“不需要独立 UI 文档”的理由。

## 7. 验收标准

模板落地后应满足：

1. 用户输入“补前端交互设计”时，AI 能建议 `docs/design/frontend-interaction.md` 路径。
2. 有独立 Web / 移动端 / 桌面端交互的项目，AI 能判断是否需要 UI 详细设计。
3. 生成的 UI 文档能追溯到 `03/04/05/07/08/09`，不新增未授权功能。
4. `docs-checklist` / `docs-system-audit` 能检查前端交互设计是否缺失或越界。
5. 模板仍保持 `docs/` 根目录只放 `README.md` 与 `00-09`，不新增 `10-ui-design` 类编号文档。
6. 文档明确前端隐藏入口不是权限边界，权限必须由后端接口和服务层执行。
