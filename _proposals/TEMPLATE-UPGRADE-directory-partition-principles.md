# TEMPLATE-UPGRADE：模板补「代码目录划分依据」——通用五条原理 + 目录→依据映射

> 来源：LUMEN-DEMO（emily8421/LUMEN-DEMO）派生项目回流
> 提案日期：2026-08-18
> 目标文件：`ai/global-rules.md` §5（通用目录标准）与 `template-docs/web-fullstack-profile.md` §4（推荐目录边界）二选一或分工承载
> 状态：**已提交模板维护者**——issue [#370](https://github.com/emily8421/ai-project-template/issues/370)（2026-08-18 开，OPEN，等维护者 triage）；本文件留作审计底稿，**勿重复提交**；与 [#357](https://github.com/emily8421/ai-project-template/issues/357)（根目录结构优化）互补不重叠——#357 管**根目录**怎么分类，本提案管**代码目录**为什么这么切

## 1. 动机

模板现有目录相关规则只给了「有哪些目录」与「边界是什么」（`global-rules §5` 目录清单 + 三层区分类框架；`web-fullstack-profile §4` 推荐目录树 + 四问），**缺「凭什么这么划分」的依据说明**。派生项目实证（LUMEN）：新会话 / 新协作者问「代码实现目录怎么划分、依据是什么」时，只能口头解释，规范里无处可指；新增目录或挪动代码时也没有判断口径，容易凭感觉放。

结构性问题：目录边界（放哪）是「果」，划分依据（凭什么）是「因」；只写果不写因，边界表无法自解释，也无法覆盖表中未列的新场景。

## 2. 拟改

在模板中补一节「目录划分依据」（去项目化表述），内容为五条通用依据 + 一句话判断口径：

| # | 依据 | 原理一句话 | 判断口径 |
|---|---|---|---|
| 1 | 部署 / 运行时边界（最外层） | 构建产物、技术栈、发布节奏不同的代码分属不同部署单元 | 这段代码跟着哪个镜像 / 构建走？不同→顶层分开 |
| 2 | 架构分层（框架内） | 关注点分离：传输 / 业务 / 数据访问 / 领域模型独立，依赖单向向下 | 改动原因归哪层就放哪层 |
| 3 | 业务特性纵切（组件内） | 同一功能的改动聚合一处，不按技术角色横切散落 | 改这个功能只动一个 feature 目录=正确 |
| 4 | 契约单源（跨端共享） | 双运行时共同认可的结构定义独立成单一事实源，双端派生防漂移 | 两端会不会各自描述同一接口？会→独立目录 + 派生校验 |
| 5 | 开发生命周期（横切面） | 源码 / 测试 / 构建 / 工具变更原因与受众不同，分开存放 | 它失效时谁受影响？受众不同→独立目录 |

附注两点（去项目化）：

- 依据引**软件工程稳定原理**（关注点分离 Parnas 1972、单一职责、同原因变更聚合 CCP、契约式设计 Meyer 1986）；主流框架布局（Django/Rails、feature-sliced、Clean Architecture）只作印证注脚，不作约束源——避免规范随框架风尚过时。
- 鼓励派生项目在 `docs/05-tech-spec.md`（或等价技术文档）登记「本项目目录 → 依据映射表」，作为边界表的前置「为什么」节。

### 落点分工建议（二选一或并采）

- **方案 A（并采，推荐）**：`global-rules §5` 目录清单后加精简五条依据（通用，所有形态适用）；`web-fullstack-profile §4` 目录树前加「依据 → 推荐树」的对应说明 + 映射表示例（Web 特化展开）。理由：§5 是所有派生项目必读，依据放那里可见度最高；profile 只在 Web 项目触发，放展开示例。
- **方案 B（单点）**：只放 `web-fullstack-profile §4`。缺点：CLI / 纯库项目读不到。

## 3. 与既有规则关系（去重）

- `global-rules §5` 目录清单 + 三层区框架——本提案**补划分依据**，不改清单与分类。
- `web-fullstack-profile §4` 四问（入口在哪 / 纵切在哪 / API client 怎么追溯 / 状态样式是否可复用）——四问即依据 #2/#3/#4/#5 的提问式变体；本提案把四问升级为显式原理表，四问可保留为速查。
- #357 根目录结构优化——管根目录分类（模板继承 / 治理记录 / 项目产出），本提案管代码目录内部分层维度；两者正交。
- `global-rules §2` L0 原则（单一职责 / 体量克制）——本提案是 L0 在**目录维度**的结构化展开，不新增原则。

## 4. 版本影响与影响面

- 方案 A：MINOR bump（两文件补说明节，无路径 / 断言变更）。
- 方案 B：MINOR bump。
- 无 `template-sync.json` 路径变更、无 `check-template` 断言变更；下行同步即生效。

## 5. 验证方式

- `scripts/check-template.sh` 自检通过。
- 行为验证：新派生项目初始化后，`global-rules §5`（或 profile §4）含五条依据；`docs/05-tech-spec.md` 生成时提示登记目录→依据映射表。

## 6. 备选方案与取舍

- **维持现状（只写边界不写依据）**：边界表无法自解释，新场景无判断口径——LUMEN 实证已暴露该缺口。
- **写成长篇参考文档（独立 methodology 文）**：与 #357 已指出的问题（根目录平铺）叠加，且依据五条本身很短，不值得独立成文；嵌入既有规则文件足够。
