# TEMPLATE-UPGRADE：评估轻量代码治理路由与规则分层地图

## 1. 动机（去项目化）

模板已按 Core、Docs、Implementation、Verification、Profiles、Governance 等影响域组织规则，并通过项目规则与 Sprint / Task 约束承接专属事实。随着规则、Profile、CI 门和技术栈约定增加，维护者仍需要反复判断：

- 一条规则是跨项目原则、实现过程 Gate、项目形态 Profile、风险关注点、技术栈写法，还是项目 / 任务专属约束？
- 同一要求是否已在多个层级重复表达，导致未来同步或修改时漂移？
- 可自动检查的 test / type / lint 要求，应作为执行 Gate 还是写进通用代码原则？

本提案不主张建立一套替代现有目录的新治理框架，而是评估是否为现有载体补一份轻量的“归类地图”，帮助规则归位、去重和按任务组合加载。

## 2. 拟评估的分类模型

### 2.1 规则内容稳定性：L0-L3

| 层 | 归类问题 | 典型内容 | 建议承载方向 |
|---|---|---|---|
| L0 通用原则 | 换任何语言、项目是否仍成立？ | 命名表达意图、失败可见、最小变更、先契约后实现 | Core 通用规则 |
| L1 职责层约束 | 换语言仍成立，但依赖代码职责吗？ | API / 业务 / 数据 / UI 的职责与依赖边界 | 项目形态 Profile 或风险包 |
| L2 技术栈约束 | 是否只适用于某语言或框架？ | 某语言或框架的具体写法 | 可选 Adapter / Profile 附录 |
| L3 项目专属约束 | 是否仅由当前项目选择或历史契约决定？ | 目录、错误契约、依赖限制、豁免与技术债 | `ai/project-rules.md` 与技术方案 |

### 2.2 任务执行路由：R1-R7

| 路由 | 回答的问题 | 优先复用的现有模板承载位 |
|---|---|---|
| R1 全局质量 | 什么是不可牺牲的质量底线？ | Core 通用规则 |
| R2 生命周期 Gate | 编码前、中、后必须完成什么？ | Implementation lifecycle、验证规则、CI 口径 |
| R3 项目形态 Profile | 这个软件形态额外需要什么？ | `template-docs/*-profile.md` |
| R4 技术风险 Concern | 本任务是否触发安全、数据、迁移、外部服务等风险？ | 现有文档 / 风险 / SOP 载体；是否补 Concern 机制待评估 |
| R5 技术栈 Adapter | 上层原则在具体语言或框架中怎样实现？ | 可选 Profile 子节或技术栈附录 |
| R6 项目基线 | 当前项目已确认什么、禁止什么？ | `ai/project-rules.md`、`docs/05-tech-spec.md` |
| R7 任务契约 | 当前任务能改什么、如何验收？ | `docs/08-dev-plan.md`、`tasks/*`、验证用例 |

L0-L3 用于判断规则的稳定性和落点；R1-R7 用于判断一次任务需要组合哪些现有规则。两者互补，不要求模板把每个文件改名或新增同名目录。

## 3. 与当前模板的关系

- 本提案优先复用 `template-docs/capability-packages.md` 的影响域表和现有路由，不替代 `ai/index.md`。
- CI 中适用的 test / type / lint 属于 R2 的可执行验证要求；它不应与 L0 通用代码原则重复定义。若 build 已覆盖类型检查，或项目形态不适用，规则应要求显式说明而非强制固定命令。
- Web 结构、浏览器 smoke 等形态规则属于 R3；框架或语言的具体约定属于 R5；项目自己的目录、接口和豁免属于 R6。
- 当前已存在或已提交的通用原则、Profile、Adapter、CI 提案均可按现有路径独立评审和落地，本提案不改变其范围、优先级或版本判断。

## 4. 维护者评估选项

| 选项 | 结论 | 收益 | 代价 / 风险 |
|---|---|---|---|
| A | 不采纳，仅维持现有影响域描述 | 零迁移成本 | 新规则仍需逐次人工判断归位与去重 |
| B（建议） | 在现有方法论文档中补充精简映射表和归类问题 | 提供一致的归位语言，复用既有目录与路由 | 需要维护一页映射，并避免把它膨胀成重复规则清单 |
| C | 完整引入 R1-R7 作为新的强制路由体系 | 形式统一、覆盖全面 | 需要评估目录、同步、自检、既有规则引用和下游迁移，范围明显扩大 |

建议先评估 B。若维护者认为现有影响域表已足够，可选择 A；只有多次试点证明映射表无法解决路由和重复问题时，才另立提案研究 C。

## 5. 非目标

- 不新增强制治理目录、默认必读规则包或全项目 CI 命令。
- 不把 L0 原则变成通用 lint 硬门，也不以工具配置替代安全、架构或数据完整性判断。
- 不要求既有派生项目重构代码、迁移文档或改写项目专属规则。
- 不修改已提交提案的内容，不绑定任何特定语言、框架或业务领域。

## 6. 影响面与版本建议

若采纳 B，预计只影响模板方法论 / 维护者索引文档，并可能在相关提案评审说明中引用；不改变普通项目的默认执行行为。

建议版本影响：`PATCH`。理由是新增的是现有规则承载关系的解释与评估准则，而不是新增默认能力或强制流程。若后续采纳 C，应另行评估为独立的 `MINOR` 变更。

## 7. 验证方式

- 人工核对映射表能将新增规则唯一归入现有承载位，且不与 `ai/index.md`、Capability Packages、Implementation lifecycle 或项目规则产生第二权威源。
- 选取至少一个通用原则、一个 CI Gate、一个项目形态 Profile、一个技术栈约定和一个任务约束，确认其归位能解释“为何在此处、何时加载、由谁验证”。
- 若模板实际采纳任何文本变更，运行模板既有自检，并检查同步清单、入口和引用是否需要随之更新。
