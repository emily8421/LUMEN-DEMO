## 1. 动机

pitfall observation log（v1.61.1 引入）的触发描述是「任务收尾自检顺带判断**本次**是否产生坑观察」——会话视角，只覆盖「AI 当场踩的坑」。派生项目实践发现一个未覆盖的高价值场景：

**维护 / 治理任务中发现的存量 AI 代码问题**。AI 生成的代码常见「障眼法」形态：类型 / 接口 / 实现看似可行、功能演示通过，实际靠巧合运行（消费方碰巧只用到了存在的字段；测试碰巧没覆盖偏差路径）。这类问题在生成时不暴露，在后续维护（类型检查器引入、契约对齐、重构）中才被发现——此时已不在「本次会话产生」的口径内，容易不记录。

实证样本（派生项目，docs/09 审计记录背书）：

- 前端手写响应类型与后端实际契约多处失配（声明字段多于运行时、optionality 不一致、两种响应形状压平为 optional 字段当运行时哨兵），运行时均「碰巧没炸」——引入 openapi codegen 对齐时集中暴露（~17 域中 3 处需修正）。
- 引入 mypy 时抓到存量真实类型 bug ~20 个（current_space_id None 传播缺口 45 处）；引入 eslint 时抓到 `rules-of-hooks` 真 bug（tsc 未拦住）。
- 共性：生成时 AI「按想象中的形状」写类型 / 实现，内部自洽（类型检查通过、演示通过），与外部契约 / 运行时不一致。

## 2. 拟改（最小增量，不改机制结构）

`ai/session-rules.md` §4.3「触发与写入」补一条触发场景（去项目化表述）：

> - **存量代码维护触发**：维护、治理、重构或引入新检查器（类型检查 / lint / 契约对齐 / 测试）时，发现既有 AI 生成代码的缺陷、「看似可行实靠巧合运行」的障眼法实现、或类型 / 接口与实际契约的失配——即使问题非本次会话产生，也应记录单条（根因分类标「AI 引入」，现象注明发现场景），作为生成规范迭代的验证材料。

并在 §4.3 开头的机制定位句补一句（与 token-hotspot 管成本、pitfall 管质量的二分对齐）：

> pitfall 记录既覆盖「当场踩的坑」，也覆盖「维护中发现的存量 AI 代码问题」——后者是检验与完善代码生成规范的主要输入。

不新增目录、不改 rollup 阈值、不加 CI 门禁（与 §4.3 既有「无自检门禁」口径一致）。
