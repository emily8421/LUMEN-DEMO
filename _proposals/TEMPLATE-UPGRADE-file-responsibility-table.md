# TEMPLATE-UPGRADE：文件治理三层体系——职责表（写之前）+ 结构检查（提交时）+ 阈值棘轮（兜底）

> 来源：LUMEN-DEMO（emily8421/LUMEN-DEMO）派生项目回流
> 提案日期：2026-08-19
> 目标文件：`template-docs/web-fullstack-profile.md` §5 / §5.1（主要）+ `ai/global-rules.md` §2 L0（可选指针）
> 状态：**已提交模板维护者**——issue [#374](https://github.com/emily8421/ai-project-template/issues/374)（2026-08-19 开，OPEN，等维护者 triage）；本文件留作审计底稿，**勿重复提交**。
> 与 [#370](https://github.com/emily8421/ai-project-template/issues/370)（目录划分依据）同主题域不同粒度：#370 管「放哪个**目录**」，本提案管「放哪个**文件**、文件里放什么」——两级互补，#370 已含五条目录依据，本提案是其文件级延伸。

## 1. 动机

模板现有文件膨胀治理（`web-fullstack-profile §5` 阈值表 + §5.1 主应用文件职责边界）存在结构性缺口：**阈值是滞后指标**。行数超标只能等文件胖了才报警，永远无法在写代码之前告诉 AI「这段代码该放哪个文件、以什么规则写入」。对 AI 编码场景，这直接导致 AI 只能靠读相邻代码归纳文件职责——归纳错误即结构劣化，且劣化在行数超标时已成事实。

派生项目实证（LUMEN，2026-08-18 逐目录评审 + 2026-08-19 根因分析）：

1. **阈值数字无推导**：250/300 是整数惯例（模板 v1.51.0 引入），行业参照系差异大（SonarQube 默认 1000 行 / Google 风格不限文件行数只限函数行数）；阈值只能当「劣化报警器」，不能当「写得对不对」的判断器。
2. **行数是代理指标**：文件超标的病因是「多个变更原因混居」（SRP 违规），行数只是间接症状；一个严格按职责写的文件行数自然落在阈值内——因果倒置时永远只能事后补救。
3. **正向规范只有雏形**：§5.1 已有「主应用文件职责白名单 + 软上限」（方向正确），但只覆盖主应用文件一类，未推广到 api / service / repository / features / hooks / store / CSS / 测试等其他文件类型。
4. **规则无机器门即会破洞**：LUMEN 实测发现明文规则「service 层不 import fastapi」已被一处既存代码突破且无豁免登记——文档规则靠 AI 自觉必漏。

## 2. 拟改

把文件膨胀治理从「单层阈值」升级为「三层体系」（规范 + 约束成对）：

```text
L1 职责表（源头规范，写之前）—— 每类文件一张三列小表：只准放 / 不准放 / 超出职责去哪
L2 结构检查（过程约束，提交时）—— 按内容拦分层违规（import 方向 / 禁止调用），不看行数；CI step
L3 阈值棘轮（兜底信号，事后）—— 既有 §5 阈值表保留，但措辞改为「症状信号」：超标≈职责混居的可疑信号，处置入口=对照职责表拆分；数字标注「约定值」
```

### 2.1 L1：职责表模板（去项目化骨架，派生项目按栈填充）

§5.1 现有「主应用文件职责边界」升级为通用模式，新增一节「文件职责表」：

| 文件类型 | 只准放 | 不准放 | 超出职责去哪 |
|---|---|---|---|
| 传输层（api / controller / router） | 路由声明、参数解析校验、调业务层、异常→HTTP 映射 | 业务规则、SQL/ORM 调用、领域计算 | 业务进 service；持久化进 repository |
| 业务层（service / use case） | 业务规则、编排持久层、领域异常、跨模块协调 | web 框架 import（豁免须登记）、HTTP 语义、SQL | 传输关注点进 api 层 |
| 持久层（repository / gateway） | 接口契约、SQL/ORM 实现、事务边界 | 业务规则、web 框架 import | 业务判断回 service |
| 前端 API client 层 | 类型定义、单出口调用封装、契约派生产物 | UI 逻辑、状态管理 | UI 进 features；跨组件状态进状态层 |
| 前端 feature 域 | 该域 UI 组件、域 hooks、域内状态 | 跨域状态 setter、别域 UI 引用 | 跨域协调经回调交应用壳编排 |
| 样式文件 | 该视图布局与组件样式、token 引用 | 字面色值 / 未登记 token | 通用值进 tokens 单源 |
| 测试 / 冒烟 | 按域命名的测试、夹具 | 业务实现、重复夹具 | 公共夹具进共享支持件 |

配套口径：

- 职责表回答「放哪个文件、文件里放什么」；目录划分依据（#370 五条）回答「放哪个目录」——两级粒度互补，判断口径一脉相承（「这行代码因为什么而变？」）。
- 落点建议：派生项目在 `docs/05-tech-spec.md`（或等价技术文档）登记按本项目栈实例化的职责表。

### 2.2 L2：结构检查建议（机制描述，不绑定具体工具）

- 检查项示例：业务层不 import web 框架（豁免清单显式登记 + 豁免失效自动检测）；传输层不 import ORM；持久层 / 模型层不 import web 框架。
- 实现零门槛：~80 行 Node 脚本（或等价 grep 脚本）+ CI 一个 step；不强制引入新依赖（import-linter 等工具列备选不列必选）。
- 模板只需在 profile 中描述机制与收益（LUMEN 实测：三条规则现状 PASS + 违规探针全拦截，CI 增量 ~秒级）；脚本样例可后续另立 scaffold 实验（同 §8 边界）。

### 2.3 L3：§5 阈值表措辞修正

- 表头「提醒阈值 / 建议动作」→「症状信号阈值（约定值）/ 处置（先对照职责表）」。
- 表前加一句定位：行数是职责混居的间接代理指标；250/300 为约定值而非推导值；处置入口 = 职责表拆分，不是机械砍行数。
- 数字本身不变（向后兼容既有派生项目基线）。

## 3. 与既有规则关系（去重）

- `web-fullstack-profile §5`（阈值表）——保留数字、修正定位（L3）。
- `web-fullstack-profile §5.1`（主应用文件职责边界）——升级为通用职责表模式的实例之一（L1），原文可保留为「主应用文件」行的展开。
- `global-rules §2` L0 原则（单一职责 / 体量克制「超阈值先拆再加功能」）——L1 是 SRP 在**文件维度**的正向结构化；L3 是「体量克制」的定位校准（阈值=症状信号），不新增原则。
- #370（目录划分依据五条）——管目录级；本提案管文件级，是其下一级粒度延伸，判断口径同源。
- `implementation-lifecycle-rules §6.2`（自动检查归位：按形态裁剪 + 显式说明）——L2 结构检查按该口径属「项目按形态声明适用检查」的实例，本提案不改变裁剪立场，只在 Web 形态 profile 中给出推荐检查项。

## 6. 备选方案与取舍

- **维持现状（只补阈值机器化）**：阈值仍是滞后指标，AI「写之前往哪写」的问题不解决——本提案的核心动机正在于此。
- **只给结构检查不给职责表**：检查项从哪来需要依据；职责表是检查项的规范源头，两者应成对。
- **模板内置检查脚本**：超出 profile「结构基线非脚手架」定位（§8 已有 scaffold 实验边界）；本提案只入方法论，脚本留派生项目自建。
