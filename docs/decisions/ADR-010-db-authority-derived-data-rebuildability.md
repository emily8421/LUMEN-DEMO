## 1. 背景与问题

2026-07-20 的 Obsidian 设计参考建议提出：数据库中的 chunks、向量、`document_relations` 等衍生数据应能从 `.md` 文件全量重建，frontmatter 是关系型字段唯一权威来源，数据库为索引缓存。

交叉核实后，该原建议与 LUMEN 当前架构不一致：

- LUMEN 已选择 PostgreSQL + pgvector 作为运行态数据底座，文档、版本、空间、权限、术语、标签、反向链接和快速录入均落 DB。
- 权限三级、空间隔离、版本历史、owner / member 关系无法仅靠 Markdown frontmatter 稳定表达。
- `.md` 在 LUMEN 中是导入源、导出格式和可迁出载体，不是运行时唯一真相源。

因此需要一个改写后的架构裁决：既保留 LUMEN DB 权威模型，又吸收 Obsidian 对可迁移、可恢复、避免索引不可解释的有效提醒。

## 3. 备选方案

| 方案 | 描述 | 优点 | 缺点 / 风险 | 验证方式 | 结论 |
|---|---|---|---|---|---|
| A：Obsidian 式 `.md` 唯一权威 | `.md` + frontmatter 是唯一真相源，DB 全部视为可丢弃索引缓存 | 数据可移植性强，灾备简单 | 与 LUMEN 已实现的权限、空间、版本、术语和 DB 模型冲突，重构成本高 | 需重写 04/06/07 与后端模型 | 放弃 |
| B：DB 全权威，不设派生可重建约束 | 所有表都视为权威运行态，不要求索引或缓存可重建 | 最贴近当前实现，短期成本最低 | chunks / embedding / 反链索引 / 计数可能变成不可解释状态，灾备和迁移风险高 | 无法从文档内容校验索引一致性 | 放弃 |
| C：DB 权威 + 衍生数据可重建 | DB 承载运行态权威；正文、版本、权限、空间、术语等为权威数据；chunks / embedding / 反链索引 / document_count 等派生数据必须能从权威内容与元数据重建 | 保留现有模型，降低索引漂移和灾备风险 | 需要后续维护每个新派生表 / 字段的重建来源与触发条件 | 06 中标注派生项；后续任务补重建脚本或一致性检查 | 采纳 |

## 4. 最终决策

- 决策：LUMEN 采用 **DB 权威运行态 + 衍生数据可重建** 模型。
- DB 权威范围：用户、空间、成员关系、文档正文、文档版本、文档权限、owner、术语、标签定义、快速录入记录等运行态业务事实以 PostgreSQL 为权威。
- 可重建派生范围：`lumen_chunks`、`lumen_chunks.embedding`、`lumen_chunks.ts_vector`、`lumen_doc_links` 的 wikilink 解析结果、标签 / 文档计数类字段等，必须能从权威文档内容、文档元数据和权限边界重新生成或校验。
- 不采纳：不采纳“frontmatter 是唯一权威来源、数据库为可丢弃缓存”的原始 OB-01 表述。
- 生效范围：自本 ADR 起，新增索引、缓存、计数、向量、解析结果类表 / 字段必须在 `docs/06-db-design.md` 说明来源、重建触发和权限过滤口径。
- 回退条件：若未来产品明确转向 local-first `.md` Vault 模型，需新 ADR 替代本决策，并重写权限 / 版本 / 空间 / 同步模型。
