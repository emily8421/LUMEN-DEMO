# 第1章 项目概述

## 1.1 项目背景

### 1.1.1 项目产生背景

随着数字化办公和 AI 技术的发展，个人与团队每天都会产生大量知识资产。

这些知识资产通常分散在多个系统中，例如：

* 本地文件夹
* 飞书云文档
* 腾讯文档
* 浏览器收藏夹
* 微信聊天记录
* 邮件附件
* AI 对话记录
* 项目资料库

当项目数量较少时，这种分散管理方式尚可接受。

但随着工作年限增加、项目数量增长，知识管理会逐渐面临以下问题：

#### 问题一：知识分散

同一个项目的信息可能分布在多个平台：

```text
需求文档 → 飞书
会议纪要 → 本地Markdown
竞品资料 → 浏览器收藏夹
设计图 → 腾讯文档
总结报告 → Word
```

需要不断切换系统才能找到完整信息。

---

#### 问题二：知识难以复用

很多有价值的内容只存在于：

* 会议纪要
* 临时调研
* AI对话
* 个人笔记

这些内容缺乏结构化沉淀。

当再次遇到类似问题时，往往需要重新搜索、重新调研。

---

#### 问题三：搜索效率低

传统文件夹管理依赖：

```text
记住文件名
记住目录位置
记住保存时间
```

当文档数量达到数百甚至数千份时：

```text
知道写过
但找不到
```

成为常态。

---

#### 问题四：AI无法理解个人知识

通用 AI 模型拥有大量公开知识。

但无法直接理解：

* 企业内部资料
* 项目历史记录
* 个人方法论
* 决策过程

因此 AI 的回答往往缺乏上下文。

---

### 1.1.2 项目建设目标

KnowledgeBase 项目希望建立：

```text
统一知识入口
        ↓
统一检索
        ↓
统一沉淀
        ↓
AI辅助利用
```

最终形成：

```text
个人知识中台
```

而不是单纯的笔记工具。

---

## 1.2 项目定位

### 1.2.1 项目定义

KnowledgeBase 是一个：

**Knowledge Management System（知识管理系统）**

简称：

```text
KMS
```

系统定位：

```text
文档管理
+
知识沉淀
+
全文检索
+
AI问答
```

---

### 1.2.2 与常见工具的关系

KnowledgeBase 并不替代现有工具。

而是作为统一入口存在。

| 工具            | 定位         |
| ------------- | ---------- |
| 飞书            | 在线协作       |
| 腾讯文档          | 在线编辑       |
| Obsidian      | Markdown笔记 |
| 本地文件夹         | 文件存储       |
| ChatGPT       | 通用AI       |
| KnowledgeBase | 统一知识入口     |

因此：

```text
飞书继续使用
腾讯文档继续使用
本地文件继续保留

KnowledgeBase负责统一管理
```

---

### 1.2.3 能力三角

KnowledgeBase 的核心能力可以概括为：

```text
        统一索引
       （找得到）
            ▲
            │
            │
AI辅助 ──────┼────── 结构化沉淀
（用得上）         （存得好）
```

---

#### 统一索引

目标：

```text
找得到
```

支持：

* 文件搜索
* 标签搜索
* 全文搜索
* AI搜索

---

#### 结构化沉淀

目标：

```text
存得好
```

支持：

* Markdown
* 模板
* 决策记录
* 方法论沉淀

---

#### AI辅助

目标：

```text
用得上
```

支持：

* AI问答
* AI总结
* AI生成内容
* 知识引用

---

## 1.3 项目目标

### 1.3.1 总体目标

KnowledgeBase 的长期目标是：

构建一个能够从个人知识库逐步演进为团队知识平台的系统。

演进路径：

```text
个人知识库
      ↓
知识管理平台
      ↓
团队知识中台
```

---

### 1.3.2 Phase 1目标

Phase 1 为：

```text
个人知识库 Demo
```

主要实现：

#### 文档管理

支持：

* Markdown浏览
* Markdown编辑
* 文件管理

---

#### 快速录入

支持：

* 飞书文档索引
* 腾讯文档索引
* 网页索引
* 本地文件索引

---

#### 全文搜索

支持：

* 文件名搜索
* 正文搜索
* 标签搜索

---

#### AI问答

支持：

* 本地知识库问答
* 来源引用
* 历史记录

---

#### 本地模型

支持：

* Ollama
* qwen3
* bge-m3

---

### 1.3.3 Phase 1不做什么

为了保证项目可落地。

Phase 1 不实现：

* 多用户
* 权限系统
* 项目空间
* PostgreSQL
* Qdrant
* 工作流引擎
* Agent平台

这些能力将在后续版本逐步增加。

---

---

### 1.4.4 演进原则

系统建设遵循：

#### 原则一：分阶段交付

每个阶段必须：

```text
独立可运行
独立可使用
```

---

#### 原则二：渐进演进

避免：

```text
一次设计全部功能
```

采用：

```text
先简单
再扩展
```

---

#### 原则三：文档优先

遵循：

```text
先文档
后代码
```

而不是：

```text
先代码
后补文档
```

---

## 1.5 项目文档体系

### 1.5.1 核心文档

KnowledgeBase 项目采用：

```text
文档驱动开发
（Document Driven Development）
```

核心文档如下：

| 文档                 | 作用    |
| ------------------ | ----- |
| kb-prd-v4.md       | 产品需求  |
| kb-architecture.md | 系统架构  |
| kb-tech-spec.md    | 技术方案  |
| kb-db-design.md    | 数据库设计 |
| kb-api-spec.md     | API设计 |
| kb-dev-plan.md     | 开发计划  |

---

### 1.5.2 文档关系

```text
PRD
 ↓
系统架构
 ↓
技术方案
 ↓
数据库设计
 ↓
API设计
 ↓
开发计划
 ↓
代码实现
```

---

### 1.5.3 文档优先级

开发过程中遵循：

```text
PRD
>
架构设计
>
技术方案
>
代码实现
```

当出现冲突时：

优先检查文档。

而不是直接修改代码。

---

### 1.5.4 AI开发中的作用

对于 Cursor 来说：

这些文档实际上就是：

```text
项目知识库
```

AI 通过读取这些文档：

```text
理解项目目标
理解系统架构
理解技术栈
理解开发边界
```

然后辅助开发。

因此：

```text
文档质量
=
AI生成代码质量
```

项目文档越完整。

AI开发效率越高。
