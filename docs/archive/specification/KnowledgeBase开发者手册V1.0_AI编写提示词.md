## 五、写作总原则

### 1. 面向初学者

不要写成专家文档。

涉及专业概念时，需要解释：

- 是什么；
- 为什么需要；
- 在本项目中怎么用；
- 初学者容易在哪里出错。

例如：

介绍 Git 时，不要只写命令，而要解释 Git 的作用是“保存项目的历史版本，方便回退和协作”。

介绍 Docker 时，不要只写安装方式，而要解释 Docker 的作用是“把运行环境打包，减少不同电脑之间的环境差异”。

### 2. 实践优先

文档应以实际操作为主，避免大段空泛概念。

每章尽量包含：

- 操作目标；
- 前置条件；
- 操作步骤；
- 命令示例；
- 验证方法；
- 常见问题；
- 注意事项。

### 3. 文档驱动开发

本项目强调：

> 先写清楚文档，再让 AI 辅助开发。

因此需要反复强调：

- README 的作用；
- docs 目录的作用；
- Cursor Rules 的作用；
- 项目设计文档的作用；
- Prompt 模板的作用；
- 为什么 AI 需要上下文。

### 4. AI Coding 风险控制

文档不能只强调 AI 提效，也要说明风险：

- AI 可能误解需求；
- AI 可能修改过多文件；
- AI 可能生成无法运行的代码；
- AI 可能破坏已有功能；
- AI 可能忽略项目已有规范。

因此需要强调：

- 小步提交；
- 先建分支；
- 每次修改前查看 Git 状态；
- AI 生成代码后人工审查；
- 使用 git restore、git reset、git revert、git stash 做恢复。

### 5. 风格要求

请使用：

- 清晰的 Markdown 标题；
- 通俗易懂的表达；
- 表格；
- 代码块；
- 流程图或流程列表；
- 检查清单；
- 示例 Prompt。

避免：

- 过度抽象；
- 只讲概念不讲操作；
- 脱离 KnowledgeBase 项目背景；
- 随意扩展到企业级复杂架构；
- 频繁改变目录结构。
