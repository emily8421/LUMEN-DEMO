## 1. 当前判断

PR #60 合并后，需求事实链已基本闭合，但严格对照 `ai/doc-standards/00-03` 后仍属于“全量追溯补强”，还不是“字段 / 表结构严格对齐”。差异集中在：

- `00` 的角色表缺少显式“目标 / 痛点”字段，下游影响未覆盖设计、验证和任务入口。
- `01` 的用户需求总览仍按 P1 / P2 / 愿景分表，字段未完全包含“用户 / 角色、价值、初步优先级”；优先级表仍按 U-ID 范围聚合。
- `02` 的 P1 REQ 已表格化，但 P2 / 愿景仍是 bullet；U→REQ 追溯字段未完全对齐标准。
- `03` 的优先级与取舍、非目标仍是 bullet；功能清单已有 F-ID，但章节命名与字段仍需对齐标准。

## 3. 修改方案

### 3.1 `docs/00-scenario.md`

1. 将“目标用户”表调整为标准字段：`角色 ID / 角色 / 目标 / 痛点 / 成功标准 / 来源锚点`。
2. 将“背景”扩展为更贴近标准的“背景与问题”，保留当前痛点 bullet，并补“业务机会 / 来源锚点”口径。
3. 将“典型场景”字段统一为：`场景 ID / 参与角色 / 触发条件 / 场景叙事 / 期望结果 / 来源锚点`。
4. 保留“场景边界与非目标”和“上游来源映射”，字段命名按标准统一。
5. 扩展“下游影响”为：`SC-ID / 影响 U-ID / 影响 REQ / 设计入口 / 验证入口 / 任务入口 / 备注`。

### 3.2 `docs/01-user-requirements.md`

1. 将 P1 / P2 / 愿景需求清单重构为统一“用户需求总览”主表，字段为：`U-ID / 用户或角色 / 用户需求 / 来源场景 / 价值 / 初步优先级 / 建议阶段 / 状态`。
2. 保留分阶段阅读便利性，可通过“建议阶段”字段表达 `[P1] / [P2] / [愿景]`，避免三套字段漂移。
3. 保留 `UFlow` 操作流表，确认字段为：`Flow ID / 参与角色 / 前置条件 / 步骤 / 成功路径 / 失败或中断路径 / 覆盖 U-ID`。
4. 保留 `AC-ID` 用户验收口径表，字段为：`AC-ID / U-ID / 用户可观察验收口径 / 不满足示例 / 备注或下游 TC`。
5. 将“优先级与阶段建议”改为逐 U-ID 表，不再只按 U-ID 范围聚合。
6. 保留“非目标与排除需求”，确保排除项可传播到 `03` 非目标。
7. 保留全量追溯矩阵，字段对齐为：`U-ID / 来源场景或输入 / 来源锚点 / 下游 REQ / 状态`。

### 3.3 `docs/02-srs.md`

1. 将“功能需求”作为唯一 REQ 主表，覆盖 REQ-001..REQ-036，字段为：`REQ-ID / 系统需求 / 来源 U-ID / 可验证口径 / 初步阶段 / 状态`。
2. P1 REQ 写清可验证口径；P2 / 愿景 REQ 保留骨架状态，写“待该阶段细化”，不提前写当前验收。
3. 保留并整理 `NFR / CON / EX` 表，确保来源、验证方式、状态清楚。
4. 删除或压缩与 REQ 主表重复的分组叙述，避免双写漂移；如保留，必须标记为“阅读索引”。
5. 将 U-ID → REQ-ID 追溯字段改为：`U-ID / REQ-ID / 覆盖说明 / 是否完整覆盖 / 备注`。
6. 保留验证入口表，当前 Phase REQ 必须能导向 AC / TC；P2 / 愿景只保留后续阶段提示。

### 3.4 `docs/03-prd.md`

1. 将“功能聚合（F-ID）”明确为标准“功能清单”，字段为：`功能 ID / 功能描述 / 覆盖 REQ / 阶段 / 交付物形态 / 状态`。
2. 将“优先级”改为“优先级与取舍”表，字段为：`功能或 REQ / 优先级 / 是否进入当前 Phase / 理由 / 风险`。
3. 保留 Phase 路线图总览和各 Phase 子节，确保每个 Phase 有功能范围、交付物形态、进入标准、退出标准、状态。
4. 将 REQ 覆盖矩阵字段对齐为：`REQ-ID / 对应功能 / 阶段 / 交付物形态 / 覆盖状态`；可保留 F-ID 列作为“对应功能”。
5. 将“非目标”改成编号表：`编号 / 非目标 / 适用范围 / 来源 / 备注`。
6. 保留证据 / 验收引用表，至少覆盖 Phase1 与主要 F-ID；P2 / 愿景写明尚无验收证据、需阶段评估。

## 4. 执行顺序

1. 先修 `00` 与 `01`，固定 `SC-ID → U-ID → AC-ID` 上游链。
2. 再修 `02`，形成统一 `REQ / NFR / CON / EX / 验证入口` 结构。
3. 再修 `03`，以 F-ID 聚合 REQ，补齐优先级取舍、非目标和证据引用。
4. 最后做一致性扫描：
   - `SC-ID → U-ID → AC-ID → REQ-ID → F-ID → Phase → TC-ID` 是否闭合。
   - P2 / 愿景是否仍保持骨架 / 待细化，未被写成当前已实现或已验证。
   - `docs/08-dev-plan.md` 与 `docs/09-verification.md` 是否仍与 `00-03` 一致。

## 5. 验收标准

| 检查项 | 通过标准 |
|---|---|
| doc-standards 最低结构 | `ai/doc-standards/00-03` 中列出的最低结构均能在 `docs/00-03` 找到等价章节或表 |
| ID 链路 | P1 至少闭合 `SC-ID → U-ID → AC-ID → REQ-ID → F-ID → Phase → TC-ID` |
| REQ 覆盖 | REQ-001..REQ-036 均有阶段归属、状态和 PRD 承接 |
| 状态准确 | P2 / 愿景保持骨架 / 待细化，不写成当前已实现或已验证 |
| 范围控制 | 不新增需求，不改 Phase 指针，不启动 Phase2 编码 |
| 格式检查 | `git diff --check -- docs/00-scenario.md docs/01-user-requirements.md docs/02-srs.md docs/03-prd.md` 通过 |
