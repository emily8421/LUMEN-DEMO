## 0. 阅读对象与使用方式

- **派生项目维护者 / AI**：把本框架当「地图」——决定一条新规范该放哪层、用什么载体、如何判断它是否通用（§3 判断方法）、如何随项目演进（§7 归纳法）。

## 1. 背景与目标

### 1.1 问题

LUMEN 是首个「研发过程文档 → AI 代码编写」的实践项目。文档体系（`docs/00-09` + `ai/`）已有较完整的规范约束，但**代码生成层面**的规范约束薄弱，表现为（2026-08-10 全栈评估实证）：

- **结构骨架已对齐**（目录边界、文件膨胀阈值、App Shell——见 `template-docs/web-fullstack-profile.md`），但**代码层一致性差**：错误处理、装配方式、类型契约、命名语义在不同模块各写各的（错误码二义、4 份重复映射、`str(exc)` 泄露内部细节、无兜底 5xx、`main.py` 18 个 `if router` 逐个注册、`*-store.ts` 命名与语义不符等）。
- 同时也有**强实践未被固化**（零 `any` + `ReturnType<typeof useXxx>`、HTTP 单出口、领域异常分离、bcrypt + 防枚举恒定时序、不透明 token 仅存摘要）——证明缺的不是能力，是「把好实践固化为可执行基线」的**规范载体与分层依据**。

### 1.2 目标

建立一套**分层的代码规范与约束体系**，让 AI 在基于文档编码时有清晰、可执行、可检查的依据，降低随机性与不一致。本框架回答四个根本问题：

1. 好代码应遵循哪些原则？（§2 质量维度体系）
2. 规范怎么分层——哪些全局、哪些按类型？（§3 分层模型）
3. 「按类型」用什么维度划分最合适？（§4 维度选择）
4. AI 编码的规范和人类编码有何不同？（§5 特殊设计原则）

## 2. 代码质量维度体系（「好代码」的目标属性）

质量维度是**目标**（好代码长什么样），与 §3 的**规则**（怎么做到）正交。软件工程公认 ~10 个维度，按优先级分三层：

### 2.1 底线（必须满足，否则不可交付）

| 维度 | 含义 | AI 编码意义 | LUMEN 实证 |
|---|---|---|---|
| **正确性** | 功能符合需求 / 契约，行为可验证 | AI 会写出「能跑但逻辑错」的代码；契约（envelope / 错误码）必须对 | `code` 字段二义（既业务码又 HTTP 码）破坏正确性契约 |
| **安全性** | 防越权、防泄露、防注入 | AI 常漏权限检查、把异常原文抛客户端 | `str(exc)` 直传泄露内部细节；弱默认 token key 无生产校验 |
| **一致性** | 项目内风格、模式、契约统一 | **AI 编码头号风险**：每个模块各写各的 | 4 份 `code→HTTP` 映射表键集不同；`main.py` 逐 router 累加 |

### 2.2 核心（强烈建议，决定长期可维护）

| 维度 | 含义 | AI 编码意义 | LUMEN 实证 |
|---|---|---|---|
| **可读性** | 别人 / 未来的自己能看懂 | AI 重写时若看不懂既有代码，就另起炉灶制造漂移 | 超长文件（`pg_repository.py` 1621 行）拖累可读性 |
| **可维护性** | 改动容易、不易引入新问题 | 体量膨胀直接破坏可维护性 | `App.tsx` 545 行上帝组件，新增任何 hook 都要改它 |
| **可测试性** | 能被自动化测试覆盖 | 没测试 = 改一处不知有没有改坏 | ~30 个后端测试从未在 CI 跑；API 测试不经 HTTP 层 |
| **健壮性** | 异常 / 边界 / 故障下不崩 | 静默吞异常、无兜底是典型缺口 | 无兜底 5xx envelope；降级 `except` 静默吞无日志 |

### 2.3 进阶（按项目阶段取舍）

| 维度 | 含义 | 何时优先 |
|---|---|---|
| **可复用性** | 代码能被复用 | 有多项目 / 多模块复用需求时 |
| **可扩展性** | 需求增长能扩展 | 进入规模化阶段 |
| **性能 / 效率** | 资源占用、响应时间 | 有明确性能目标或资源约束时 |

### 2.4 阶段化取舍（重要）

并非所有维度同等重要，**按项目阶段降级**。Demo / MVP 阶段（如 LUMEN）：**一致性、正确性、安全性、可读性、可维护性**为核心；性能 / 可扩展性 / 可复用性可降级（`ai/project-rules.md §2.1` 资源软上限是同一思路在资源层的体现）。进入规模化 / 上线阶段再升格进阶维度。

## 3. 代码规范分层模型（L0–L3）

这是本框架的核心。规范按「通用 → 专属」分四层，每层换到不同项目 / 语言时稳定性递减：

```
L0  通用代码原则      换任何语言、任何项目都成立              【最稳定】
L1  架构职责层约束    按代码职责层（API/业务/数据/UI）分      跨语言稳定
L2  技术栈 / 语言约束 Python / TS-React / Go 各怎么写         语言特有
L3  项目专属约束      LUMEN 的 envelope、表前缀、不引状态库   项目独有   【最易变】
```

### 3.1 L0 通用代码原则（全局，所有代码）

**定义**：与语言、技术栈、项目类型无关的「写代码基本功」。换到 CLI 工具、纯计算库、Web App、移动端都成立。

**示例**：命名传达意图、单一职责、一致性优先、失败必须可见（禁静默吞）、不重复（DRY）、显式优于隐式、对外信息最小化、可测试性、变更最小与可追溯、import / 依赖卫生、体量克制、先契约后实现。

**具体清单**：见 `_proposals/TEMPLATE-UPGRADE-global-rules-l0-code-principles.md`（B 提案，12 条带可执行口径）。

**载体建议**：模板 Core 层 `ai/global-rules.md §2 AI 代码生成规范`（现状仅「生成前 / 时 / 后」三句高层要求，**缺 L0 基线**——见 §6 缺口）。

### 3.2 L1 架构职责层约束（跨语言，按职责层）

**定义**：按代码在架构中的「职责层」划分——API / 控制器层、业务 / 服务层、数据 / 持久层、UI 层——各层该做什么、不做什么、边界在哪。**跨语言稳定**（Python FastAPI、Java Spring、Node Express 的「业务层不依赖 web 框架」都成立）。

**示例**：service 层不 import web 框架（抛领域异常，api 层转 HTTP）；API 层只做协议转换不含业务逻辑；数据层不含业务规则；装配（main / 入口）与逻辑分离；依赖方向单一（上层依赖下层，不反向）；对外契约（envelope / 错误码 / 类型）稳定一致。

**载体建议**：按项目形态进 Profiles 层（如 `template-docs/web-fullstack-profile.md §9` 的「代码层一致性基线」是 Web 全栈的 L1+L2 合并载体）。

### 3.3 L2 技术栈 / 语言约束（语言特有）

**定义**：具体语言 / 框架的写法约束。换语言即不成立。

**示例**：
- **Python**：`snake_case` + 类型注解 + import 收敛顶部 + 禁裸 `except` + 用 `logging` 不用 `print` + `requirements` 精确锁版。
- **TypeScript / React**：禁 `any` + hooks 规则 + 组件单一职责 + 禁过深 prop drilling + `tsconfig strict` + `ReturnType<typeof useXxx>` 零重复类型。

**载体建议**：进 Profiles 层的「语言专属小节」，或项目 `docs/05-tech-spec.md §4`（LUMEN 已有）。

### 3.4 L3 项目专属约束（项目独有）

**定义**：本项目特有，换项目不成立。

**示例（LUMEN）**：统一 envelope `{code,msg,data}`、表前缀 `lumen_`、不引路由库 / 状态库 / UI 库、embedding 固定 `bge-small-zh` 512 维、AI 调用走 OpenAI 兼容 adapter。

**载体建议**：`ai/project-rules.md §5`（精炼，每次任务必读）+ `docs/05-tech-spec.md §4`（详细）。LUMEN 已回填（`§4.1` 结构膨胀 + `§4.2` 代码层一致性，含【已落地】/【待对齐】分级）。

### 3.5 判断一条规范属于哪层的方法

沿用 `ai/doc-standards/project-rules.md` 的判断标准，具体到代码规范：

- 「换到另一个**完全不同的项目**还成立吗？」→ 不成立 = **L3 项目专属**。
- 「换一种**编程语言**还成立吗？」→ 不成立 = **L2 语言特有**；成立但只在某种架构形态 = **L1 职责层**。
- 「换任何语言、任何项目都成立？」→ 是 = **L0 通用**。

> 示例：「service 不得 import fastapi」——换 Spring/Express 也成立（业务层不依赖 web 框架），属 **L1**；「禁 `any`」——只对 TS 成立，属 **L2**；「envelope `{code,msg,data}`」——只 LUMEN 成立，属 **L3**。

## 4. 「按类型」划分的维度选择

回答「用技术栈？编程语言？编程工具？哪种划分最合适？」

### 4.1 主维度：项目形态 / 场景（用 Profile）

**为什么用它做主划分**：项目形态（Web App / CLI / 纯库 / 移动端）决定「要哪些层、哪些目录、哪些质量维度优先、怎么测」，是最稳定、最贴近「这个项目需要什么」的划分。模板已用此维度做 **Profile**（`web-fullstack-profile.md`、`remote-ci-sop-profile.md`；机制见 `template-docs/capability-packages.md`）。

### 4.2 正交子维度：职责层 × 技术栈

在 Profile **内部**，用两个正交子维度组织规则：
- **职责层**（API / 业务 / 数据 / UI）：决定「代码该做什么」，跨语言稳定（§3.2 L1）。
- **技术栈 / 语言**：决定「代码该怎么写」（§3.3 L2）。

二者正交：一条「业务层不依赖 web 框架」是语言无关的（L1），同时「禁 any」只对 TS 成立（L2）。

### 4.3 不用：编程工具

**不按 Claude / Cursor / Codex 等工具划分**。理由：工具会变、会换，规范应独立于工具。模板 `ai/global-rules.md §7` 已体现「切换工具丢失对话历史，但不丢失项目规则」——规则载体（文件）与工具解耦，按工具分规范会破坏这一原则。

### 4.4 稳定性排序（决定规范放哪层）

`项目形态 < 编程语言 < 编程工具` 的变化频率递增，故规范应绑定**稳定**的维度（项目形态 / 职责层 / 语言），而非**易变**的维度（工具）。越稳定的维度，越适合沉淀为跨项目同步的模板内容。

## 5. AI 编码规范的特殊设计原则

AI 基于文档编码的失败模式很集中（LUMEN 评估印证），规范设计需区别于「给人看的代码规范」：

| 原则 | 含义 | 口号 vs 可执行口径（对比） |
|---|---|---|
| **① 可执行口径** | 规则要具体到能 grep / 能 lint，而非原则口号 | ❌「写清晰的代码」 ✅「`service/` 目录不得 `import fastapi`」「`fetch` 只允许出现在 `api/client.ts`」 |
| **② 禁区优先** | AI 对「不要做什么」的遵守好于「要做什么」；每层都要有禁区清单 | ❌「注意错误处理」 ✅「禁 `str(exc)` 直传客户端」「禁静默吞异常」 |
| **③ 强制对齐既有** | AI 本能是另起炉灶，必须明确「新代码向既有看齐，不引入同类不一致」 | ❌「保持一致」 ✅「新增 API 资源 = 新建 `api/<resource>.ts` + barrel re-export，不得新建平行入口」 |
| **④ 体量阈值防膨胀** | AI 倾向「在一个文件里继续加」，需硬阈值提醒 | `web-fullstack-profile §5`（App 300 / service 250 / CSS 300）已是范例 |
| **⑤ 机械化检查优先** | 能写成 lint / grep / CI 门的，比靠 AI 自觉强 10 倍 | LUMEN CI 零代码门是反面教材；`tsconfig strict:true` 是正面教材 |

> 这 5 条是「规范该怎么写」的元规则，适用于 L0–L3 所有层。

## 7. 推进方法论：归纳法（给非专家项目主）

**核心建议：用归纳法，不用演绎法。**

- ❌ 演绎法：先设计一套「完美的代码规范分类学」再套到所有项目。样本不足时，设计易空、易错。
- ✅ 归纳法：每做一个项目，做一次「代码评估 → 规范回流」（如 LUMEN 这次）。**积累 2–3 个不同形态的项目后，「哪些是全局（L0）、哪些是特化（L1–L3）」自然浮现**——多项目都犯的错 = L0 候选；只在某类项目出现的 = 该形态特化。

### 7.1 归纳流程（每项目）

1. 评估：抽样审查代码，列「好实践（可固化为规范）+ 技术债（需规范约束）」，每条带文件:行证据。
2. 分层：用 §3.5 判断方法，把每条归入 L0–L3。
3. 落地：L3 → 项目 `project-rules §5` + `docs/05 §4`；L1+L2 → 形态 Profile（起草 TEMPLATE-UPGRADE 提案）；L0 候选 → 暂存，待多样本验证后升格。
4. 沉淀：把本次评估 + 分层写成研究备忘（如本文件），作为下一项目的参照基准。

### 7.2 LUMEN 是第 1 个样本

LUMEN = Web 全栈样本（React + FastAPI + PG）。已完成评估 + 分层 + 落地（提案 ×2 + `docs/05 §4.2` + `project-rules §5` + 本框架）。建议第 2 个样本选**不同形态**（如 Python CLI 工具、纯前端组件库），每个都问「这条 LUMEN 也有吗？」——有 → L0 候选升格；无 → 形态特化。

> 好处：**不必先成为软件工程专家**。规范从真实痛点归纳，不空。LUMEN 已迈出第一步。

## 8. 回流路径（本框架如何回到项目模板）

本框架（§1–§7）本身去项目化（框架通用，LUMEN 仅作实证举例），具备回流条件。

### 8.1 建议的模板承载形态（二选一或合并）

- **(a) 融入现有载体**：把本框架的「代码规范分层（L0–L3）+ 维度选择 + AI 编码原则」作为 `template-docs/capability-packages.md`（影响域分层索引）的「代码规范分层映射」补充 + `template-docs/template-methodology.md` 的方法论补充。优点：不新增文件、融入现有分层叙事。
- **(b) 新增独立载体**：新增 `template-docs/code-constraint-framework.md`。优点：单一主题集中、易引用。

### 8.2 回流时机
