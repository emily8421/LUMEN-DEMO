# 文件治理机制根本性分析：从「阈值报警」到「职责规范 + 约束」分层体系（2026-08-19）

> **定位**：`docs/research/` 评估报告，非权威规格。分析对象 = 当前文件膨胀治理机制（`docs/05-tech-spec.md` §4.1 阈值表 + `check-frontend-file-size.mjs` 棘轮）的根本缺陷与升级方案。
> **性质声明**：本文是 **AI 分析结论与建议草案，待人工确认采纳范围**；在用户裁决前不改变任何现行规范，不触发代码修改。
> **触发背景**：用户对 R1（后端补 file-size ratchet）提出根本性质疑——阈值是怎么取的？只有定阈值一种方法吗？阈值是滞后指标（等超出后果了才处理），AI 无从知道「哪些内容可否写入这些文件、应该以怎样的规则写入」。本文回答这三个问题。

## 0. 一句话结论

**阈值是「体重秤」不是「食谱」**：它只能等文件胖了才报警，永远无法在写代码之前告诉 AI「这段代码该放哪个文件」。行数只是「一个文件混进了多个变更原因」的**间接代理指标**。治理「代码往哪写」的正确体系是三层：**职责白名单（源头规范，写之前）→ 结构检查（过程约束，提交时机器拦）→ 阈值棘轮（兜底信号，事后）**。本仓三层现状：白名单有雏形未成体系、结构检查只有零星几个、阈值棘轮前端有后端没有——**唯一机器化了的恰恰是最末端的兜底层**。

## 1. 用户三个问题的直接回答

### Q1：250/300 这个阈值是怎么取的？

**诚实答案：方向有学科依据，数字是约定值，没有推导过程。**

来源链追溯（本仓 Git 可证）：

```text
模板仓 ai-project-template · template-docs/web-fullstack-profile.md §5
  → 2026-07-14 随 v1.51.0 同步进本仓（commit 230992e）
  → 抄录进 docs/05-tech-spec.md §4.1 阈值表
  → 2026-08 前端机器化（check-frontend-file-size.mjs + .file-size-baseline.json 棘轮）
```

- **「文件应该小、超限该拆」有依据**：单一职责原则（一个模块一个变更原因）、DeMarco 关于模块规模的讨论（出处见 `docs/references/software-engineering-basics.md` §3「service 超阈值文件」行）。模板文档自己也定性了：**「治理提醒，不是硬性编译规则」**（web-fullstack-profile §5 原文）。
- **「250/300」两个具体数字没有推导**：是整数惯例值。行业参照系差异很大——SonarQube 默认文件上限 1000 行；Google 风格指南不限文件行数、只限函数行数；没有权威出处支持 250 是正确分界线。
- **结论**：阈值 = 「劣化报警器」，不是「写得对不对」的判断器。它回答的是「这个文件是不是已经大到可疑」，不是「这段代码该不该进这个文件」。

### Q2：只有定阈值这一种方法吗？

**不是。阈值只是四层手段中最末端的一层。** 行业成熟实践按「介入时机」分四层：

| 层 | 手段 | 回答什么问题 | 介入时机 | 本仓现状 |
|---|---|---|---|---|
| L1 正向职责规范 | 「这个文件只准放什么」白名单 | **写之前**：什么内容可以进这个文件 | 编码前对表 | ⚠️ 有雏形、未成体系（§3.1） |
| L2 结构约束机器化 | 依赖方向 / 禁止调用检查（import-linter、dependency-cruiser、自写脚本） | **提交时**：结构违规即 CI 失败，不看行数 | 提交 / CI | ⚠️ 零星有（CSS token 检查、契约测试、零 any），核心分层规则无机器门（§3.2） |
| L3 阈值 + 棘轮 | 行数超标报警 + 基线只进不退 | **事后兜底**：防继续劣化 | 事后 | ✅ 前端有 / ❌ 后端没有（= R1） |
| L4 评审问题 | 「这行代码改了是因为 HTTP 变了、业务变了还是存储变了？」 | 事中人工/AI 判断 | 设计 / 评审 | ✅ 有（05 §4.1.0 判断口径列） |

### Q3：为什么阈值治不了「AI 不知道往哪写」？

**因为行数是代理指标，不是病因本身。** 反例可直接观察：

- `backend/service/export.py` 576 行——行数不是罪，罪在导出编排 + ZIP 打包 + 文件名生成 + 权限校验四件变更原因不同的事混居一个文件（SRP 违规）。若这四件事恰好写得紧凑，450 行也同样是病；反之一个纯编排文件 400 行可能完全健康。
- 反过来说，**一个严格按职责白名单写的文件，行数自然落在阈值内**——阈值报警的文件几乎必然是职责混居的文件。这就是「白名单管源头、阈值管兜底」的因果关系：行数超标是**症状**，职责混居是**病**，棘轮只是症状监测仪。

用户观察到的「等发生后果了才处理」正是代理指标的固有局限：**症状可测、病因不可测时，永远只能事后补救**。要让 AI 写之前就知道往哪写，必须把病因本身（职责边界）写成可查的规范 + 可机器判定的约束。

## 2. 现状盘点：本仓治理机制三层对照

### 2.1 L1 正向职责规范——有雏形，未成体系

已存在的正向规范（散落各处）：

| 规范 | 出处 | 覆盖 | 缺陷 |
|---|---|---|---|
| 主应用文件职责白名单（只准组合装配 / 跨域编排 / 横切包装 / 启动装配四件事 + useState/handler 软上限 10-15 个） | 模板 §5.1 | 仅主应用文件一类 | 未推广到其他文件类型 |
| api 层职责（只做参数解析 → 调 service → 转 envelope） | 05 §4.2 / 评审证实执行好 | 后端 api 层 | 无对应机器门 |
| `*-store.ts` = localStorage 序列化层 | 05 §4.2 命名语义 | 前端 store 类 | 命名约定，无检查 |
| 目录划分五依据 + 判断口径（「这行代码因为什么变就放哪层」） | 05 §4.1.0 | 目录级 | 是「放哪个目录」不是「放哪个文件、文件里放什么」 |

**缺口**：没有一张「每类文件 × 只准放什么 / 不准放什么 / 超了去哪」的职责表。AI 编码时对文件的预期只能靠读相邻代码归纳——这正是「不知道以怎样的规则写入」的根源。

### 2.2 L2 结构约束机器化——零星有，核心分层规则无门

已有机器门：CSS token 检查（check-frontend-css.mjs）、零 `any`（eslint）、契约测试（test_repository_contract.py）、schema-diff/codegen drift、PG fail-closed guard。这些都是「看内容不看行数」的结构检查，证明本仓有能力做 L2。

**关键缺口 + 实证**：05 §4.2 明文「service 不 import fastapi」，但本次核查发现 `backend/service/auth_context.py:22` 已 `from fastapi import Depends, Header, HTTPException`——**规则只有文档、没有机器门，靠 AI 自觉，已经破了洞且无豁免登记**。（顺带：auth_context 定位是「鉴权依赖项」供 router 共用 `Depends(get_current_user)`，属 fastapi 传输层关注点渗入 service 层的边界案例，不是恶意违规；但正因如此才需要机器门——边界案例靠自觉必漏。）repository/model 层核查无 fastapi 泄漏。

### 2.3 L3 阈值棘轮——前端有、后端没有

即 R1 所述治理不对称。本报告不重复论证，仅指出：**在 L1/L2 建立后，R1 的优先级可从「高」降为「中」**——因为后端超限文件（6 个 service + pg/demo repository）的病因若由 L1 职责表 + L2 结构检查管住，行数自然收敛，棘轮只剩兜底作用。但这不否定 R1：三层是互补不是替代，棘轮仍是零成本防线。

## 3. 建议方案：三层文件治理体系（规范 + 约束成对）

### 3.1 L1 职责表（正向规范——回答「什么可以写入这个文件」）

设计原则：**每类文件一张三列小表：只准放什么 / 不准放什么 / 超出职责的去处**。落点 `docs/05-tech-spec.md` §4.1（阈值表旁），模板侧回流 web-fullstack-profile §5.1（推广「主应用文件白名单」模式）。

草案（以本仓现有代码事实校准，**待裁决后逐行确认**）：

| 文件类型 | 只准放 | 不准放 | 超出职责去哪 |
|---|---|---|---|
| `backend/api/*.py` | 路由声明、参数解析与校验、调 service、异常→HTTP 映射、response_model 装配 | 业务规则、SQL/ORM 调用、领域计算、直接读写 repository 实体 | 业务进 service；持久化进 repository |
| `backend/service/*.py` | 业务规则、编排 repository、领域异常、跨模块协调 | `import fastapi`（豁免须登记）、HTTP 语义（状态码/Header）、SQL | 传输关注点进 api 层或独立 auth_context 类豁免件 |
| `backend/repository/*.py` | Protocol 定义、SQL/ORM 实现、持久化事务边界 | 业务规则、HTTP 语义、fastapi import | 业务判断回 service |
| `backend/model/*.py` | dataclass 实体、ORM 映射、Pydantic schema、错误码常量 | 任何 I/O、业务流程 | — |
| `frontend/src/api/*.ts` | 类型定义、client 调用封装、契约派生（generated） | UI 逻辑、状态管理、DOM | UI 进 features；跨组件状态进 app hooks |
| `frontend/src/features/<域>/` | 该域全部 UI 组件、域 hooks、域内状态 | 跨域状态 setter、别域 UI 引用 | 跨域协调经回调交 app 层编排 |
| `frontend/src/app/use*.ts` | 单域状态与副作用、可复用 hook | 跨域 setter、UI 渲染 | 跨域编排回 useAppState / 主文件 |
| `frontend/src/app/*-store.ts` | localStorage 读写与序列化 | 响应式状态、业务规则 | 业务进域 hook |
| CSS（每视图一文件） | 该视图布局与组件样式，token 引用 | 字面色值 / 字阶 / 圆角（已有 CI 门） | 通用值进 tokens.css |
| `tests/` / `scripts/smoke-*` | 按域命名的测试 / 冒烟 | 业务实现、重复的测试工具函数 | 公共夹具进 pg_test_support 类共享件 |

配套两个口径：
- **行数阈值的定位改写**：阈值表措辞从「提醒阈值→超阈值处理」改为「**症状信号**：超标≈职责混居的可疑信号，处置入口 = 对照职责表拆分」，把阈值显式降级为 L3 兜底（数字本身可保留 250/300，诚实标注「约定值，非推导值」）。
- **职责表与 05 §4.1.0 的关系**：五依据管「放哪个**目录**」，职责表管「放哪个**文件**、文件里放什么」——两级粒度互补，判断口径一脉相承（「这行代码因为什么而变？」）。

### 3.2 L2 结构检查（机器约束——提交时拦，不看行数）

全部零额外成本（无付费工具、无新依赖）：

| 检查 | 实现 | 拦什么 |
|---|---|---|
| `service 不 import fastapi` | 自写 ~30 行脚本（grep + 白名单豁免清单），CI 一步 | 传输层渗入业务层（现 auth_context.py 即漏网案例，登记豁免后基线化） |
| `api 层不出现 SQL/ORM 调用` | 同上（检测 `from backend.model.orm import` / `session.` 等模式） | 传输层绕过 service 直捣存储 |
| `repository/model 不 import fastapi` | 同上（现状已 0 违规，检查防回归） | 同上 |
| 既有 CSS token / 零 any / 契约测试 | 已有 | 不变 |

> 备选：引入 import-linter（免费 pip 包，声明式契约）可少写自研脚本，但新增依赖与 05 §4「Sprint 内不引基线外依赖」约束相抵，**建议自写脚本**（与既有 check-* 系列同构，~100 行内）。

### 3.3 L3 棘轮（= R1，兜底不动摇）

前端已有；后端补齐（R1 原方案），在 L1/L2 之上作为最后一道防线。三层关系：**白名单管源头 → 结构检查管过程 → 棘轮管兜底**，互不替代。

### 3.4 与文档体系的对照（为何文档侧不需要此改造）

文档体系已是「规范 + 约束」双件齐全：`ai/doc-standards/<doc>.md` 定义每份文档必含字段/ID/矩阵/禁止项（= L1 职责表），`ai/prompts/review/` checklist + docs-evaluation 审计（= L2/L4）。**代码侧缺的正是文档侧已有的那张「职责表」**——本建议实质是把文档治理的成熟模式移植到代码治理。
