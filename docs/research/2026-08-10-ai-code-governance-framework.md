## 0. 本文要解决什么问题

LUMEN 是一个典型的“文档体系逐步成熟，但代码约束后补”的 AI 研发项目。功能可以持续交付，不代表实现方式会自然收敛。若 AI 每次只收到当前功能目标，它通常会优先选择“这一次最快能跑通”的写法，而不会自动维护跨 Sprint 的分层、错误契约、事务、权限、类型同步、测试边界和文件职责。

因此，真正要解决的问题不是“再写一份 Python 或 React 编码规范”，而是建立一套能够持续回答以下问题的治理系统：

1. 对所有项目都成立的代码质量原则是什么？
2. 哪些规则只在特定项目形态、技术风险、语言或框架下触发？
3. AI 在一次任务开始前，如何知道该加载哪些规则，而不是凭记忆选择？
4. 哪些要求只靠文字提醒，哪些必须由 lint、类型检查、测试、构建或 CI 自动阻断？
5. 项目中发现的好实践与坏模式，如何经过验证后回流模板，而不是把某个项目的偶然写法推广成全局规则？
6. 规则如何保持“少而硬”，避免规则越来越多、相互重复、AI 反而无法稳定执行？

本文给出的核心结论是：

> **代码治理不应按“编程语言文件夹”简单堆规则，而应采用“分层规则 + 条件路由 + 自动化执行 + 证据回流”的体系。**

语言、框架和工具很重要，但它们主要负责把上层原则落成具体写法和检查命令，不应成为治理体系唯一或最高层的分类方式。

## 1. 结论摘要

### 1.1 推荐的总体模型

建议项目模板使用七层路由规则（R = Routing），并用一条独立的“自动化执行平面”贯穿各层。使用 R1-R7 是为了与前置研究的 L0-L3 内容稳定性分层区分：

| 层级 | 回答的问题 | 典型内容 | 是否跨项目 |
|---|---|---|---|
| R1 全局质量宪章 | 什么叫“好代码”？优先级是什么？ | 正确性、安全性、可读性、可维护性、可验证性 | 是 |
| R2 实现生命周期 Gate | AI 在编码前、中、后必须做什么？ | 先读契约、限制范围、验证、回写证据 | 是 |
| R3 项目形态 Profile | 这是什么类型的软件？ | Web 全栈、CLI、库 / SDK、数据流水线、移动端 | 条件复用 |
| R4 技术风险 Concern Pack | 这次功能触发了什么高风险机制？ | 认证授权、数据库事务、迁移、文件导入、LLM、外部 API | 条件复用 |
| R5 技术栈 Adapter | 用当前语言 / 框架如何实现上层规则？ | FastAPI、React、PostgreSQL、Python、TypeScript 口径 | 条件复用 |
| R6 项目专属基线 | 本项目已经选择了什么、禁止什么？ | 目录、命名、错误码、命令、依赖、历史债与豁免 | 否 |
| R7 任务局部契约 | 当前任务允许改什么，如何验收？ | 输入文档、修改范围、不变量、测试与禁止事项 | 否 |

自动化执行平面包括 formatter、lint、类型检查、单元测试、契约测试、集成测试、构建、smoke、依赖与安全扫描、CI Gate。它不是第八套“理念规则”，而是把前七层中可机器判断的条目变成稳定反馈。

### 1.2 判断全局规则与专属规则的最简单方法

对每条候选规则依次问五个问题：

1. 换成完全不同的软件项目仍然成立吗？成立则优先归 R1 或 R2。
2. 只要项目形态相同就成立吗？成立则归 R3 Profile。
3. 只要触发某类技术风险就成立吗？成立则归 R4 Concern Pack。
4. 只是把上层原则翻译成某种语言 / 框架写法吗？是则归 R5 Adapter。
5. 只因本项目的技术选择、历史契约或阶段边界才成立吗？是则归 R6；只对当前任务成立则归 R7。

例如：

| 规则 | 正确归属 | 原因 |
|---|---|---|
| 权限校验必须位于可信边界，不能只靠 UI 隐藏 | R1 / R4 安全 | 与语言和框架无关 |
| 多步写操作必须明确原子性与回滚 | R4 数据事务 | 只要涉及持久化写入就触发 |
| FastAPI service 层不得抛 `HTTPException` | R5 FastAPI Adapter | 是“领域层不依赖传输框架”的 FastAPI 实现方式 |
| React 组件使用 PascalCase | R5 React / TypeScript Adapter | 语言生态惯例 |
| LUMEN 前端 HTTP 必须经 `api/client.ts` | R6 项目基线 | 依赖 LUMEN 当前目录和客户端设计 |
| 本任务只允许修改导入服务和对应测试 | R7 任务契约 | 仅对本次任务成立 |

### 1.3 与 L0-L3 内容分层的关系

两套编号回答不同问题，不应二选一：

| 前置研究 L0-L3 | 本文 R1-R7 中的主要落点 | 说明 |
|---|---|---|
| L0 通用代码原则 | R1 全局质量宪章；部分进入 R2 Gate | 描述跨项目稳定内容；R 视角补充何时检查和如何执行 |
| L1 架构职责层 | R3 Profile + R4 Concern；通用底线可提升 R1 | 职责边界需结合项目形态和具体风险触发 |
| L2 技术栈 / 语言 | R5 Adapter | 两者直接对应 |
| L3 项目专属 | R6 项目基线 | 两者直接对应 |
| 前置研究未单列 | R2 生命周期、R7 任务契约 | 是本文为 AI 执行闭环增加的正交过程层 |

因此，L0-L3 适合模板维护者判断“一条规则有多通用、应该放哪里”；R1-R7 适合 AI 在一次任务中判断“这次要加载和执行哪些规则”。

### 1.4 好代码的优先级

所有质量目标都重要，但发生冲突时不能平均用力。推荐默认优先级：

> **安全与数据完整性 > 功能正确性 > 清晰与可变更性 > 可验证与可运行性 > 性能优化与局部优雅。**

这意味着：

- 会误删真实数据的快速测试，即使执行方便，也不可接受；
- 会产生越权读取的高性能查询，即使响应更快，也不可接受；
- 一个可读、可测试的重复实现，通常优于尚无真实复用价值的复杂抽象；
- 性能优化应有测量证据，不能以牺牲正确性和可维护性为默认代价。

## 2. 为什么仅靠“编码规范”不够

### 2.1 编码风格只是最外层一致性

缩进、命名、引号、import 顺序和格式化可以提高表面一致性，但 LUMEN 的主要风险并不在这里。现有评估发现的高优先级问题包括：

- 数据库集成测试可能连接默认开发库并执行 `TRUNCATE ... CASCADE`；
- CI 没有运行后端测试、前端类型检查、构建或 lint；
- 多个 repository 方法各自提交，跨方法业务用例缺少统一事务；
- 权限过滤依赖 service 调用者先加载全量数据再过滤；
- 前端把结构化 API 错误压成字符串，再靠文案正则判断登录过期；
- 后端没有 `response_model`，前后端类型靠手工双写；
- repository 双实现没有显式 Protocol，接口一致性靠开发者记忆。

这些问题分别属于测试安全、交付 Gate、事务边界、授权边界、错误契约、类型契约和可替换性。即使所有文件都通过 formatter，也不会自动解决。

### 2.2 “按语言分规范”会遗漏跨语言系统契约

如果只建立 Python 规范和 TypeScript 规范，API envelope、错误码、鉴权、分页、日期格式、幂等性和 schema 同步会落在两份规则之间，无人负责。前后端各自“符合语言规范”，系统仍可能在边界处失败。

因此，治理对象应优先按以下顺序识别：

1. 系统不变量和风险；
2. 模块边界与跨层契约；
3. 项目形态与运行方式；
4. 技术栈的具体实现；
5. 语言风格与工具配置。

### 2.3 工具不是原则，而是执行器

Ruff、Mypy、ESLint、TypeScript、pytest、Playwright、Alembic 都不应该自行定义项目“为什么这样做”。正确关系是：

```text
质量原则 / 风险约束
        ↓
可执行规则与项目口径
        ↓
工具配置、测试和 CI
        ↓
失败证据与修复反馈
```

例如，“禁止前端组件直接访问后端”是架构约束；ESLint 的 restricted import 或全仓检查只是执行方式。“迁移必须可追踪且不可重复执行”是数据完整性约束；Alembic 是一种实现工具，不是约束本身。

## 3. 好代码应遵循的质量原则

### 3.1 可行性（Feasibility）

定义：实现能够在目标环境、资源、依赖、时间和团队能力范围内真实运行，而不是只在 AI 的假设环境中成立。

必须关注：

- 运行时、操作系统、硬件和资源上限；
- 外部服务、网络、密钥和依赖是否真实可用；
- Demo、Mock、降级和生产实现的边界；
- 安装、启动、迁移和恢复步骤是否可重复；
- 新依赖的维护成本、许可和供应链风险。

LUMEN 依据：项目明确锁定 Node、Python、本机 GPU / 内存和 LLM 降级边界，这是良好基础；但 CI 未实际覆盖前端构建和后端代码测试，意味着“本机曾经可运行”尚未转化为持续可行性证据。

治理要求：任何技术选型或新依赖都必须给出环境前提、失败方式、替代方案和验证命令。

### 3.2 正确性（Correctness）

定义：实现对正常输入、边界输入、错误输入和并发条件都满足需求、业务不变量和接口契约。

必须关注：

- 需求与实现之间有可追溯锚点；
- 输入校验位于可信边界；
- 状态转换只允许合法路径；
- 空值、重复、超限、并发和部分失败有明确语义；
- 错误不是“被吞掉后继续”，而是可预测地传播或降级。

LUMEN 依据：多步 import / 更新流程分别调用会提交的 repository 方法，若后一步失败，前一步可能已永久生效。这不是代码格式问题，而是业务原子性未被明确。

治理要求：每个写用例在编码前列出前置条件、后置条件、不变量、失败语义与幂等性。

### 3.3 可读性（Readability）

定义：读者能够在合理时间内理解代码的目的、边界、数据流和异常流，不依赖原作者或聊天历史。

必须关注：

- 名称表达真实职责，不用误导性术语；
- 函数和模块具有单一、可描述的目的；
- 控制流平直，避免深层嵌套和隐式副作用；
- 注释解释“为什么”和不明显的约束，而不是记录 Sprint 拼接史；
- 公共契约和复杂算法有必要说明。

LUMEN 依据：部分 `*-store.ts` 实际只是 localStorage 序列化函数，命名却暗示响应式状态仓库；代码中还混有大量 Sprint / Phase 过程注释。两者都会让后续 AI 根据错误语义继续扩展。

治理要求：评审名称时检查“一个陌生开发者是否会据此做出正确假设”；过程历史放 Git、任务和文档，不堆入业务代码。

### 3.4 简单性（Simplicity）

定义：在满足当前需求和已确认扩展点的前提下，使用最少必要概念、状态、层级和依赖。

必须关注：

- 不为未确认的未来需求预建复杂框架；
- 不用抽象掩盖尚未理解的差异；
- 重复达到稳定模式后再抽取；
- 优先使用标准库、项目既有模式和成熟组件；
- 每个新层、helper 或依赖都能说明减少了什么复杂度。

治理要求：AI 提出新抽象时必须说明至少两个真实调用方、被消除的重复或被隔离的风险；否则保持局部直接实现。

### 3.5 模块化与可变更性（Modularity and Changeability）

定义：需求变化可以局限在清晰的模块内，不要求同时理解和修改大量无关代码。

必须关注：

- 业务、传输、持久化、外部服务和 UI 职责分离；
- 依赖方向稳定且可解释；
- 接口显式，替代实现可由类型和测试验证；
- 文件大小只是信号，更重要的是职责数量和变化耦合；
- 跨模块写操作有统一编排点。

LUMEN 依据：`pg_repository.py` 和 `demo_repository.py` 分别超过 1,600 行和 1,200 行，并承载约百个方法；双实现无 Protocol。这使一次接口变化需要靠人工记忆同步多个巨型文件。

治理要求：按业务能力或聚合边界拆接口，避免“一仓储包含全系统”；对多实现接口使用 Protocol / ABC / interface 和契约测试。

### 3.6 安全、隐私与数据完整性（Security, Privacy, Integrity）

定义：系统在恶意输入、身份冒用、越权、错误配置和操作失误下仍保护数据、权限与敏感信息。

必须关注：

- 认证、授权、数据作用域和审计；
- secret 管理、弱默认值和启动期校验；
- 注入、路径遍历、反序列化和文件处理；
- 错误信息不泄露堆栈、路径、SQL 或敏感原文；
- 测试、迁移和运维脚本具有环境护栏；
- 数据删除、覆盖和批量修改可确认、可回滚或可恢复。

LUMEN 依据：PostgreSQL 测试使用默认 `DATABASE_URL` 且设置阶段执行 `TRUNCATE ... CASCADE`，缺少“必须是测试数据库”的硬断言；权限查询也有先读取全量集合、再由 service 过滤的模式。这两项分别威胁数据完整性和最小权限边界。

治理要求：安全规则优先在 repository / query / transaction / runtime guard 等可信边界执行，不能只依赖调用者记得过滤或 README 提醒。

### 3.7 可靠性与可恢复性（Reliability and Recoverability）

定义：依赖失败、超时、重试、进程重启和部分故障不会让系统处于不可解释或无法恢复的状态。

必须关注：

- 强依赖失败时 fail fast，弱依赖才允许明确降级；
- 超时、重试、退避和幂等性协同设计；
- 事务、补偿和重放语义明确；
- migration 有账本、顺序和失败恢复；
- 后台任务、导入和同步可以断点续作或安全重跑；
- 健康检查反映真实 readiness，而不是进程仍存活。

LUMEN 依据：数据库初始化失败后主进程可能继续启动，健康状态与实际可服务能力可能不一致；迁移采用重放脚本但缺少成熟 ledger。这些会把启动成功误判为系统可用。

治理要求：对每个外部依赖标明“强依赖 / 可降级依赖”，分别定义启动、运行期和恢复策略。

### 3.8 可测试性与可验证性（Testability and Verifiability）

定义：关键行为可以用稳定、隔离、可重复的方式证明，而不是依赖“AI 认为逻辑正确”或人工偶然点通。

必须关注：

- 单元、契约、集成、端到端测试各自负责不同风险；
- 测试默认隔离外部依赖和真实数据；
- 测试失败有确定原因，不因顺序或环境随机波动；
- API 必须经过真实序列化 / 反序列化边界测试；
- 验收标准在编码前确定；
- 修复缺陷时先形成回归用例或最小复现。

LUMEN 依据：后端已有较多测试和 smoke，这是资产；但 CI 不执行代码 Gate，API 测试多直接调用函数，前端没有单元测试，浏览器脚本还重复维护连接工具。因此“测试数量”尚未转化为稳定回归能力。

治理要求：测试覆盖按风险分层，不追求单一覆盖率数字；P0 安全边界和跨层契约必须有不可绕过的 Gate。

### 3.9 可观测性与可运维性（Observability and Operability）

定义：系统失败时能知道发生了什么、影响谁、处于哪个请求或任务，并能通过受控步骤启动、停止、诊断和恢复。

必须关注：

- 统一日志接口、级别、上下文字段和关联 ID；
- 不用 `print` 混入运行日志；
- 降级和重试必须留下原因；
- 指标、健康检查和 readiness 与业务能力一致；
- 配置来源集中且可审计；
- runbook 与实际命令一致。

LUMEN 依据：存在 `print` 与 logging 混用、部分宽泛异常静默吞掉、配置分散读取等问题。故障发生时，行为可能对用户表现为“没有结果”，但日志没有足够证据。

治理要求：所有容错分支必须在“用户可理解结果”和“工程可诊断证据”两端同时闭环。

### 3.10 性能与资源效率（Performance and Efficiency）

定义：系统在已确认规模和响应目标下，以可接受的 CPU、内存、I/O、网络和成本完成工作。

必须关注：

- 先定义目标规模和预算，再优化；
- 数据查询在存储层裁剪作用域和字段；
- 避免 N+1、无界列表、重复序列化和重复外部调用；
- 批处理、缓存和并发不能破坏一致性；
- LLM / 外部 API 还需控制 token、费用、速率和超时。

LUMEN 依据：部分权限路径先加载全局文档或成员集合再过滤，不仅扩大越权风险，也会随数据量放大内存与查询成本。

治理要求：性能优化必须附测量方法和基线；安全作用域过滤应尽量下推到查询层，同时改善安全与效率。

### 3.11 兼容性与可复现性（Compatibility and Reproducibility）

定义：相同源码和锁定输入在受支持环境中能得到一致结果，升级和契约变化有明确边界。

必须关注：

- 运行时与依赖版本锁定；
- 数据库 schema、API schema 和客户端类型同步；
- 向后兼容、弃用和迁移策略；
- 时间、时区、编码、路径分隔符和换行差异；
- 构建产物与环境配置可复现。

LUMEN 依据：项目已有运行时锁定意识，但前后端契约仍手工双写，且 CI 尚未构建前端或验证 schema 漂移。

治理要求：跨进程、跨语言边界优先使用机器可读 schema，并用生成或 diff 检查维持一致。

### 3.12 用户体验与可访问性（UI 项目条件触发）

定义：对有 UI 的项目，代码不仅“功能能调用”，还应使关键流程可理解、可操作、可恢复，并覆盖键盘、焦点、语义和错误反馈等可访问性要求。

必须关注：

- loading、empty、error、disabled、permission denied、conflict 等状态完整；
- 错误信息能指导用户下一步，不暴露内部细节；
- 键盘操作、焦点管理、语义标签和对比度；
- 响应式范围与项目已确认设备一致；
- UI 隐藏不被当作权限实现。

治理归属：这是 Web / 移动 / 桌面 Profile 的条件规则，不应强加给纯 CLI 或库项目；但“错误可理解”和“权限必须在可信边界执行”仍是全局原则。

## 4. 七层代码治理路由体系

### 4.1 R1：全局质量宪章

目的：定义所有项目共同遵守的价值排序与不可突破底线。

建议只保留少量高强度条目：

1. 不得以牺牲安全、数据完整性或正确性换取交付速度。
2. 代码必须满足已确认需求和契约，不自主扩展功能。
3. 重要边界必须显式：输入、输出、错误、权限、事务、外部依赖。
4. 优先选择项目既有模式和最简单可验证实现。
5. 所有变更必须有与风险相称的验证证据。
6. 可机器检查的规则应自动化；不能自动化的规则必须给审查问题和例外机制。
7. 规则变更需要来源、依据、适用条件和回退方式。

不建议在本层写：React 组件命名、pytest marker、FastAPI 异常类型、某个目录路径。这些会让全局层快速膨胀。

### 4.2 R2：实现生命周期 Gate

目的：约束 AI 的工作过程，防止它只关注代码输出。

建议设置四个 Gate：

| Gate | 进入条件 | 必须产出 | 未满足时 |
|---|---|---|---|
| G0 任务可实施 | 需求、范围、依赖和验收明确 | 输入文档、允许修改范围、非目标 | 不编码，先补缺口 |
| G1 设计可实施 | 关键边界和风险已定义 | 数据流、错误流、权限 / 事务 / 外部依赖策略 | 不进入业务实现 |
| G2 代码可合入 | 本地快检通过 | format、lint、type、相关测试、build 证据 | 不提交 / 不合并 |
| G3 交付可验收 | 集成与用户路径通过 | 契约 / 集成 / smoke、文档和技术债回写 | 不声称完成 |

这四个 Gate 是跨项目通用的，但每个项目执行什么命令由 R3-R6 决定。

### 4.3 R3：项目形态 Profile

目的：按软件“如何被使用和交付”加载结构、测试和运维规则。

建议初期只维护四类有明显差异的 Profile，避免过度细分：

| Profile | 触发条件 | 特有关注点 |
|---|---|---|
| Web / 全栈应用 | 浏览器 UI + API / 后端 | App Shell、API 契约、前后端类型、UI 状态、浏览器 smoke |
| CLI / 自动化工具 | 命令行参数、stdin/stdout、退出码 | 参数契约、退出码、幂等、dry-run、文件安全、跨平台 |
| 库 / SDK | 被其他代码依赖 | 公共 API 稳定、语义版本、兼容矩阵、文档示例、无副作用 import |
| 数据 / AI 流水线 | 批处理、模型、数据集、任务编排 | 数据 lineage、可重跑、checkpoint、随机种子、成本、模型 / 数据版本 |

移动端、桌面端、嵌入式等只有在出现真实项目并发现稳定差异后再新增。不要因为“可能以后用到”预建大量空 Profile。

LUMEN 归属：复杂 Web / 全栈 Profile，同时叠加数据导入、认证授权、数据库、LLM 等 Concern Pack。

### 4.4 R4：技术风险 Concern Pack

目的：只要功能触发某类高风险机制，就加载相应规则，不受项目形态限制。

建议优先沉淀以下 Concern Pack：

| Concern | 触发信号 | 最小规则 |
|---|---|---|
| 认证与授权 | 登录、token、角色、空间 / 租户、用户数据 | 身份校验、可信边界授权、作用域查询、禁枚举、审计、secret |
| 数据库与事务 | 持久化写入、多表更新、迁移 | 原子性、回滚、幂等、连接与事务所有权、测试库护栏、迁移 ledger |
| 文件与导入 | 上传、解压、路径、OCR、批量导入 | 大小 / 类型限制、路径遍历、防炸弹、临时文件、原子导入、失败报告 |
| 外部 API | 网络调用、webhook、第三方 SDK | timeout、重试、退避、幂等、签名、限流、熔断、契约测试 |
| LLM / AI | prompt、RAG、模型输出、外发数据 | 数据边界、prompt injection、结构化输出、成本、超时、降级、评测 |
| 异步任务 | 队列、定时任务、后台处理 | 去重、重试、死信、状态机、可观测、取消与恢复 |
| 缓存与并发 | cache、锁、乐观并发、实时协作 | 一致性模型、失效、竞争、版本号、冲突处理 |
| 删除与批处理 | 清理、归档、批量更新、测试 reset | 明确目标、环境断言、dry-run、确认、备份 / 恢复 |

Concern Pack 的价值是防止“认证规则只写在 Web 规范里”“事务规则只写在 PostgreSQL 规范里”。例如 CLI 也可能操作数据库，数据流水线也可能处理敏感文件，它们同样需要风险规则。

### 4.5 R5：技术栈 Adapter

目的：把 R1-R4 翻译成当前语言和框架可直接执行的模式、配置和命令。

Adapter 应包含：

- 推荐目录与依赖方向；
- 语言命名、类型与异常约定；
- 框架边界的具体类型和 helper；
- formatter / lint / type / test / build 命令；
- 常见危险默认值与禁止模式；
- 最小好 / 坏代码示例；
- 版本兼容范围。

示例映射：

| 上层原则 | FastAPI / Python Adapter | React / TypeScript Adapter | PostgreSQL Adapter |
|---|---|---|---|
| 领域层不依赖传输框架 | service 不 import / 抛 `HTTPException` | hook 不直接处理原始 `Response` | 不适用 |
| 契约单一事实源 | Pydantic request / response model + OpenAPI | 从 OpenAPI 生成或校验类型 | schema migration 为 DB 契约源 |
| 错误结构化 | 领域异常 + 集中 HTTP 映射 | `ApiError(code, message, status)` | SQLSTATE 转领域错误 |
| 自动验证 | Ruff、Mypy、pytest | ESLint、`tsc`、Vitest、Playwright | migration check、集成测试 |
| 事务明确 | Unit of Work / transaction context | UI 只表达提交状态与冲突 | 单一事务所有者、约束与锁策略 |

Adapter 不应重复写“为什么必须授权”“为什么不能误删数据”；它只说明在该栈如何做到。

### 4.6 R6：项目专属基线

目的：记录已确认、每次任务都必须遵守的项目事实和裁剪结果。

建议项目基线至少回答：

1. 当前启用哪些 Profile、Concern Pack 和 Adapter？
2. 目录边界与依赖方向是什么？
3. API、错误、日期、分页和身份上下文契约是什么？
4. 哪些命令是 format、lint、type、unit、integration、build、smoke？
5. 哪些模块或文件未经确认不能改？
6. 新依赖、迁移、配置和 secret 如何管理？
7. 当前有哪些历史技术债，新代码采用什么 ratchet 规则？
8. 哪些规则被豁免，原因、所有者和到期条件是什么？

LUMEN 已在 `ai/project-rules.md §5` 与 `docs/05-tech-spec.md §4.2` 开始补这层，但仍需把“已落地规范”“历史技术债”“自动化命令”分清。项目基线不应复制几十页通用规则，只保留选择结果、项目具体路径和命令，并引用上层规则 ID。

### 4.7 R7：任务局部契约

目的：把宏观规范转成当前改动的明确边界，防止 AI 顺手改造整个系统。

每个任务至少包含：

```markdown
## 实现契约

- 目标：本次要实现或修复的行为。
- 输入权威：REQ / API / DB / 设计章节。
- 修改范围：允许修改的模块或文件。
- 非目标：明确不做的功能和重构。
- 不变量：权限、事务、兼容性、数据完整性要求。
- 触发规则：Web Profile；数据库事务 Concern；FastAPI Adapter。
- 验证：必须执行的命令和人工路径。
- 交付证据：测试结果、差异摘要、文档 / 技术债回写。
```

任务契约的核心不是形式，而是让 AI 在改代码前先说清“什么不能被破坏”。

## 5. 规则应该怎样写，AI 才能稳定执行

### 5.1 规则条目的标准结构

每条可复用规则建议包含以下字段：

| 字段 | 作用 |
|---|---|
| ID | 稳定引用，如 `SEC-AUTH-003`、`DB-TXN-002` |
| 层级 / 来源 | R1-R7、来源项目或标准 |
| 触发条件 | 什么情况下必须加载 |
| 强度 | MUST / SHOULD / MAY |
| 规则正文 | 一句话、可判断的要求 |
| 理由 | 防止什么失败或维护成本 |
| 反例 | AI 容易生成的错误方式 |
| 正例 | 最小可接受模式 |
| 自动验证 | 命令、lint、测试或脚本 |
| 人工审查 | 机器无法判断时问什么 |
| 例外 | 谁批准、为何、何时到期 |
| 迁移策略 | 旧代码如何渐进对齐 |

### 5.2 一个合格规则示例

```yaml
id: DB-SAFE-001
layer: concern/database
trigger: 任何测试、脚本或命令会清空、覆盖或批量修改数据库
strength: MUST
rule: 执行破坏性 SQL 前必须同时验证测试环境标记和测试数据库命名；任一不满足立即失败。
rationale: 防止测试或维护脚本误连接开发、预生产或生产数据库。
bad_example: 使用默认 DATABASE_URL，setUp 中直接 TRUNCATE 全表。
good_example: LUMEN_ENV=test 且数据库名以 _test 结尾，否则抛出异常。
automated_check: 集成测试启动 guard + CI 独立测试数据库。
manual_review: 检查命令是否还可被自定义 URL 绕过。
exception: 不允许永久例外；临时数据修复必须走独立审批与备份流程。
```

它比“测试要注意安全”更有效，因为触发、行为、验证和例外都明确。

### 5.3 MUST、SHOULD、MAY 的使用

- **MUST**：违反会导致安全、数据完整性、契约、构建或核心维护边界失效，应由 Gate 阻断。
- **SHOULD**：默认必须遵守，但存在可解释的项目权衡；豁免需留痕。
- **MAY**：推荐模式或备选，不应被 CI 当成失败。

不要把所有偏好都写成 MUST。规则全是强制时，真实项目只能通过忽略规则继续前进，最终会削弱整个体系的可信度。

### 5.4 规则的三个必要属性

1. **可触发**：AI 能根据任务文本、目录或技术选择判断是否适用。
2. **可判定**：能够回答“这次是否符合”，不能只写“保持高质量”。
3. **可验证**：至少有自动检查或明确人工审查问题。

缺任一项的文字更像价值宣言，不适合作为编码 Gate。

## 6. AI 编码的标准工作流

### 6.1 编码前

AI 应按固定顺序完成：

1. 读取项目入口、当前阶段和任务权威文档；
2. 识别项目形态 Profile；
3. 扫描本任务触发的 Concern Pack；
4. 加载相关语言 / 框架 Adapter；
5. 读取项目专属基线与质量命令；
6. 写出任务局部契约；
7. 识别数据、权限、事务、错误、外部依赖和兼容性不变量；
8. 说明预计文件、风险与验证方式；
9. 输入或设计不足时停止编码，先补决策。

建议 AI 在真正编辑前输出一个短摘要：

```text
任务类型：Web API 写路径
触发规则：Web Profile + Auth Concern + DB Transaction Concern + FastAPI Adapter
关键不变量：仅当前空间 owner 可写；写入与审计记录同事务；错误码不变
修改范围：service、repository、API contract test
验证：ruff + mypy + unit + contract + targeted integration
```

### 6.2 编码中

AI 应遵守：

- 以最小 vertical slice 实现一个完整行为；
- 不扩展未授权功能，不做无关重构；
- 新代码先遵循目标基线，历史债使用 ratchet，不复制旧坏模式；
- 在可信边界执行权限、输入校验和数据作用域；
- 多步写入先确定事务所有者，再调用 repository；
- 跨层数据使用明确 schema / DTO，不泄露内部对象；
- 错误保持结构化，日志保留诊断信息，用户消息不泄密；
- 只有真正降低复杂度时才新增抽象；
- 修改公共契约时同步消费者、测试和文档。

### 6.3 编码后

建议验证顺序从快到慢：

1. formatter / 静态语法；
2. lint；
3. 类型检查；
4. 受影响单元测试；
5. 契约测试；
6. 相关集成测试；
7. build；
8. 用户主路径 smoke；
9. 全量回归或扩展检查；
10. `git diff`、文档、技术债和验收证据复核。

AI 最终不能只说“实现完成”，而应说明：改了什么、为什么符合契约、执行了哪些验证、哪些未执行及剩余风险。

## 7. 自动化执行平面

### 7.1 四级质量命令矩阵

每个项目都应在项目基线中登记真实命令，而不是让 AI 每次猜：

| 级别 | 目标时长 | 典型内容 | 何时运行 |
|---|---:|---|---|
| Fast | 秒级到 2 分钟 | format check、lint、type、受影响单测 | 每次本地改动后 |
| Required CI | 5-15 分钟 | 全量 unit、契约测试、前端 build、schema 检查 | 每个 PR / main push |
| Extended | 可更长 | 数据库集成、浏览器 E2E、迁移往返、安全扫描 | 夜间、手动或高风险 PR |
| Release | 依发布而定 | 生产构建、迁移演练、smoke、回滚检查 | 发布前 |

### 7.2 不同工具解决什么问题

| 工具类别 | 能发现 | 不能替代 |
|---|---|---|
| Formatter | 格式漂移 | 架构、命名语义、业务正确性 |
| Lint | 常见缺陷、危险模式、依赖限制 | 事务和权限设计 |
| 类型检查 | 接口不匹配、空值和重构风险 | 运行期权限与数据库行为 |
| 单元测试 | 局部规则和边界条件 | 跨进程契约、真实数据库 |
| 契约测试 | API schema、错误 envelope、消费者兼容 | 完整用户工作流 |
| 集成测试 | 数据库、外部适配器、迁移 | UI 交互与浏览器状态 |
| E2E / smoke | 真实主路径 | 完整边界组合与内部可维护性 |
| 安全 / 依赖扫描 | 已知漏洞、secret、供应链风险 | 业务越权和数据作用域设计 |
| CI | 稳定执行上述检查 | 自动产生正确规则 |

### 7.3 Ratchet：新代码先变好，旧代码渐进迁移

存量项目常无法一次清偿全部技术债。建议使用 ratchet：

- 不要求本次无关任务重写所有旧代码；
- 新增和修改行不得引入同类问题；
- 修改到高风险旧模块时，至少补最小回归保护；
- 指标不得恶化，例如超阈值文件数量、`any` 数量、裸 `fetch` 数量、未类型化公共接口数量不能增加；
- 技术债有 ID、风险、影响范围、触发修复条件和目标时间；
- 安全、数据破坏和错误权限边界不适用长期豁免，必须优先修复。

### 7.4 例外机制

必要例外应包含：

```text
规则 ID：
例外范围：
业务 / 技术原因：
替代控制：
风险接受人：
生效日期：
到期或复审条件：
清理任务：
```

没有期限和替代控制的“临时例外”会自然变成永久架构，因此不能只写一句“历史原因”。

## 8. LUMEN 如何映射到这套体系

### 8.1 已有基础

LUMEN 并非没有规范。现有良好实践包括：

- 文档驱动的需求、设计、计划与验证链；
- 后端 api / service / repository / model 分层已形成；
- 前端 HTTP 入口向 `api/client.ts` 收敛；
- TypeScript strict 与前端泛型已有基础；
- 领域异常、认证安全和若干跨用户回归已落地；
- 有较丰富的后端测试和 smoke 脚本；
- 已有 Web App Structure Profile 和文件膨胀阈值意识。

问题不是“推倒重来”，而是已有好实践尚未全部变成统一、可执行、持续验证的基线。

### 8.2 现有问题的分层归属

| LUMEN 发现 | 规则归属 | 应落的控制 |
|---|---|---|
| 测试可能清空默认数据库 | R1 安全 + R4 DB / 删除 Concern | 测试库双重 guard、独立 CI DB、破坏性命令 fail closed |
| CI 无代码门 | R2 Gate + R6 项目基线 | 明确 quality 命令，PR 必跑 unit / type / build / lint |
| DB 失败后继续启动 | R4 可靠性 + R5 FastAPI Adapter | 强依赖 fail fast、readiness 真实反映 DB |
| Repository 巨型且双实现无契约 | R1 可变更性 + R5 Python Adapter | 分域 Protocol、契约测试、按聚合渐进拆分 |
| 多步写入无统一事务 | R4 DB Transaction Concern | service / UoW 拥有事务、repository 不独立 commit |
| 权限由 service 事后过滤 | R4 Auth Concern + DB Concern | scoped repository query、默认拒绝、越权回归 |
| 错误被前端压成字符串 | R3 Web Profile + R5 前后端 Adapter | `ApiError`、集中映射、契约测试 |
| API 与 TS 类型手工双写 | R3 Web Profile + R5 Adapter | response model、OpenAPI codegen / diff |
| migration 无 ledger | R4 DB Concern + R5 PostgreSQL Adapter | 正式迁移账本、顺序、幂等与恢复测试 |
| App 与功能文件持续回堆 | R3 Web Profile + R6 Ratchet | 文件职责阈值、changed-file Gate、拆分 ticket |
| 前端零单测、smoke 工具重复 | R3 Web Profile + R2 Gate | 最小 Vitest / RTL 层、共享浏览器 harness |
| 日志与异常处理不一致 | R1 可观测性 + R5 Python Adapter | 统一 logging、禁静默吞、结构化上下文 |

### 8.3 现有 Web 全栈提案应如何定位

`_proposals/TEMPLATE-UPGRADE-web-fullstack-code-consistency-baseline.md` 已经覆盖错误契约、分层、类型、工程化与命名，作为第一份实证提案是有价值的。但从本文分层看，它混合了三类内容：

1. 跨项目通用：CI 至少执行 test / type / lint；错误不泄露内部细节；关键 secret 不能使用弱默认值。
2. Web Profile：前后端 schema 同步、HTTP 单出口、结构化客户端错误、契约序列化测试。
3. 技术栈 Adapter：FastAPI service 不抛 `HTTPException`、Python Protocol、React `ReturnType`、具体工具名。

因此，回流模板时建议保留该提案作为实证输入，但不要把所有条目原样固定在一个 Web 文档中。模板维护者应把稳定的跨项目原则提升到 R1 / R2，把真正的 Web 共同规则留在 Profile，把 FastAPI / React / PostgreSQL 示例放进 Adapter 或示例区。

这不是否定现有提案，而是给它一个更清晰的父级框架，减少未来 CLI、数据流水线或 Java 项目重复发明同类规则。

## 9. 推荐的模板文件组织

### 9.1 原则：少文件、强路由、可执行

模板不宜一开始就为每个语言、框架、风险创建几十个文件。建议先采用“核心少量文件 + 条件章节”，内容增长或出现独立维护节奏后再拆分。

推荐目标结构：

```text
ai/
├─ rules-core.md                       # 只负责入口、路由、硬安全规则
├─ implementation-lifecycle-rules.md  # R1 质量宪章 + R2 Gate 的权威入口
└─ project-rules.md                    # R6 项目选择结果、命令、豁免与禁区

template-docs/
├─ code-governance-framework.md        # 本文去项目化后的说明与规则写法
├─ profiles/
│  ├─ web-fullstack.md                 # R3
│  ├─ cli.md
│  ├─ library-sdk.md
│  └─ data-ai-pipeline.md
├─ concerns/
│  └─ code-risk-packs.md               # 初期一文件分章节；成熟后再按风险拆
└─ stack-adapters/
   └─ README.md                        # 先放选择矩阵与少量成熟 Adapter
```

这是目标建议，不是要求当前模板立即改目录。为减少同步和引用迁移风险，第一阶段可以只在现有 `implementation-lifecycle-rules.md` 与 `template-docs/web-fullstack-profile.md` 中增补稳定内容，并通过 `_proposals/` 逐步验证。

### 9.2 项目只保存“选择结果”，不复制模板全文

项目层建议使用紧凑清单：

```yaml
code_governance:
  profiles: [web-fullstack]
  concerns: [auth, database-transaction, file-import, llm]
  adapters: [python-fastapi, typescript-react, postgresql]
  commands:
    format_check: <项目命令>
    lint: <项目命令>
    typecheck: <项目命令>
    unit: <项目命令>
    contract: <项目命令>
    integration: <项目命令>
    build: <项目命令>
    smoke: <项目命令>
  ratchets:
    - no_new_any
    - no_new_raw_fetch
    - no_new_unscoped_repository_query
  exceptions: []
```

具体载体可以仍是 Markdown 表格，不强制 YAML。关键是字段稳定，AI 能在任务开始时快速获得选择结果。

### 9.3 路由算法

AI 每次任务可按以下伪代码选择规则：

```text
load(R1_global_quality, R2_lifecycle_gates)
load(project.selected_profiles)

for risk in detect_risks(task, changed_paths, referenced_docs):
    load(concern_pack[risk])

for stack in project.active_stack:
    if task_touches(stack.paths):
        load(adapter[stack])

load(project_baseline)
load(task_contract)
```

`detect_risks` 初期不必做复杂 AI 分类器，可以根据任务关键词和路径建立简单触发表。例如出现 migration、transaction、repository、DELETE、TRUNCATE 就加载数据库 / 删除 Pack；出现 token、role、owner、member 就加载认证授权 Pack。

## 10. 从项目经验回流模板的流程

### 10.1 五阶段晋升

一条实践不应因为在 LUMEN 中出现一次就立刻成为全局 MUST。建议按以下阶段晋升：

1. **项目发现**：记录具体问题、证据、影响和本地修复。
2. **项目规则**：同项目重复出现或风险重大，写入 R6 并自动化。
3. **第二项目验证**：在不同类型或不同技术栈项目中验证其是否仍成立。
4. **分类与去项目化**：判定归 R1 / R2、Profile、Concern 或 Adapter，删除 LUMEN 路径和偶然实现。
5. **模板提案与回测**：提交提案，增加触发、例外、验证和迁移策略，再用第三个项目验证可用性。

### 10.2 晋升条件

候选规则满足以下多数条件才适合回流：

- 防止真实缺陷、安全风险或高频维护成本；
- 在至少两个独立场景中成立，或虽只出现一次但风险为灾难级；
- 能清楚定义适用条件和不适用条件；
- 不依赖某个项目的内部路径或命名；
- 有自动验证或明确审查方法；
- 不与现有规则重复，或能合并 / 删除旧规则；
- 对存量项目有渐进迁移策略。

### 10.3 用不同项目验证，而不是只复制 LUMEN

建议至少选择四类样本：

| 样本 | 验证重点 |
|---|---|
| LUMEN 复杂 Web 全栈 | 跨层契约、认证、DB、LLM、长期演进 |
| 小型 CLI | 证明全局规则不会强迫创建不需要的 Web 分层；验证文件安全和退出码 |
| 数据 / AI 流水线 | 验证可重跑、数据 lineage、模型与成本规则 |
| 库 / SDK | 验证公共 API、兼容性、版本与消费者契约 |

如果一条规则只对 LUMEN 有意义，就保留在 R6；如果只对 FastAPI 有意义，就放 Adapter；不要为了“看起来系统化”强行提升到全局层。

## 11. 推荐实施路线

### 11.1 第一阶段：先封住高风险缺口

目标：让规范开始保护代码，而不是继续扩写文本。

LUMEN 建议优先完成：

1. 测试数据库双重 guard，默认命令绝不触碰开发库；
2. CI 增加最小后端 unit、前端 type / build；
3. 明确质量命令矩阵；
4. 为结构化错误和 API envelope 增加 HTTP 契约测试；
5. 建立 changed-file ratchet，禁止技术债数量继续增长。

模板建议同时完成：

- 在实现生命周期规则中补 R1 最小质量宪章和 G0-G3 Gate；
- 定义规则条目结构、MUST / SHOULD / MAY 和例外格式；
- 现有 Web 提案按本文分层做去重审查。

### 11.2 第二阶段：补齐高价值 Concern Pack

优先顺序建议：

1. 数据库 / 事务 / 破坏性操作；
2. 认证授权；
3. 文件导入；
4. 外部 API 与 LLM；
5. 异步任务、缓存和并发。

选择依据是风险，不是文档对称性。没有真实项目证据的 Pack 先不写满。

### 11.3 第三阶段：建立少量 Stack Adapter

先从已有项目成熟实践中提取：

- Python + FastAPI；
- TypeScript + React；
- PostgreSQL；
- 后续在其他项目出现后再补 CLI、数据框架或其他语言。

每个 Adapter 必须附最小工具配置和验证命令，否则容易退化为风格建议清单。

### 11.4 第四阶段：跨项目验证与精简

每轮模板升级后问：

- 哪些规则从未触发，可以删除或降为示例？
- 哪些规则反复被豁免，说明层级或强度是否错误？
- 哪些人工检查可以自动化？
- 哪些规则重复表达同一不变量，可以合并？
- AI 是否能在不加载全量规则的情况下正确路由？

治理成熟度不以规则数量衡量，而以缺陷提前发现率、例外透明度、验证稳定性和规则执行成本衡量。

## 12. 常见错误做法

### 12.1 为每种工具单独建一套最高层规范

问题：原则重复、跨层契约无人负责，换工具时体系整体失效。

改进：工具进入 Adapter 和自动化执行平面；安全、正确性、事务和契约保留在上层。

### 12.2 把所有经验都写进全局规则

问题：CLI 被迫遵守 React 规则，库项目被迫创建 service / repository，AI 加载内容过多。

改进：用 Profile、Concern 和 Adapter 条件加载。

### 12.3 只有“最佳实践”，没有失败条件

问题：“注意安全”“保持可维护”无法判定，也无法阻断错误代码。

改进：规则写触发、MUST 行为、反例、验证和例外。

### 12.4 一次性清偿所有历史技术债

问题：改动面巨大、回归风险高，功能开发和治理都停滞。

改进：P0 立即修；其余用 ratchet 和按触达迁移。

### 12.5 只增加 CI，不设计规则

问题：CI 只能稳定执行已有检查；错误的测试、危险默认数据库或缺失的权限断言仍可能“全部通过”。

改进：先明确风险和不变量，再选择对应检查。

### 12.6 只写规则，不让 CI 执行

问题：AI 在长任务或新会话中会遗漏，人也会因交付压力跳过。

改进：能自动化的 MUST 必须进入本地命令和 Required CI。

### 12.7 把代码行数当作唯一质量指标

问题：短文件也可能职责混乱，长文件也可能是稳定数据表或生成代码。

改进：行数只作为触发审查的信号，同时评估职责数量、依赖方向、变化频率和测试隔离。

## 13. 可直接用于模板评审的检查表

### 13.1 规则体系检查

- [ ] 是否有少量、明确的全局质量优先级？
- [ ] 是否有编码前 / 中 / 后的 Gate，而非只有代码风格？
- [ ] 是否按 Profile、Concern、Adapter 条件加载？
- [ ] 项目专属事实是否与模板通用规范分开？
- [ ] 当前任务是否有修改范围、不变量和验证契约？
- [ ] 每条 MUST 是否可判定、可验证？
- [ ] 是否有例外、到期和替代控制？
- [ ] 新规则是否先尝试合并或删除旧规则？

### 13.2 代码实现检查

- [ ] 输入、输出、错误、权限和事务边界是否显式？
- [ ] 是否选择了最简单、与项目既有模式一致的实现？
- [ ] 新抽象是否解决真实重复或隔离真实风险？
- [ ] 跨层 / 跨进程契约是否有 schema 和契约测试？
- [ ] 强依赖失败是否 fail fast，降级是否可观察？
- [ ] 测试是否隔离真实数据和外部环境？
- [ ] 新代码是否没有扩大既有技术债？
- [ ] 是否执行了与风险相称的验证？

### 13.3 回流模板检查

- [ ] 是否有项目代码或失败案例作为证据？
- [ ] 是否至少在第二种场景验证，或属于灾难级单例风险？
- [ ] 是否已去除项目路径、业务名和偶然技术选择？
- [ ] 是否选对 R1-R7 路由层，并与 L0-L3 内容层正确映射？
- [ ] 是否说明不适用条件？
- [ ] 是否提供自动化和存量迁移策略？
- [ ] 是否与现有提案、Profile 或规则去重？

## 14. 待人工确认的关键决策

本文建议不直接视为已批准模板方案。需要人工确认：

1. 是否采纳“R1-R7 七层路由 + 自动化执行平面”作为模板代码治理的执行分类，并保留 L0-L3 作为内容稳定性分类？
2. R1 质量宪章与 R2 Gate 是否优先合并进现有 `ai/implementation-lifecycle-rules.md`，而不是新增更多入口规则？
3. 现有 Web 全栈代码一致性提案是否在回流前按“全局 / Web Profile / Stack Adapter”重新分类？
4. 第一批 Concern Pack 是否按“数据库事务与破坏性操作、认证授权、文件导入、外部 API / LLM”排序？
5. 项目质量命令矩阵采用 Markdown 表还是结构化 manifest；无论选择何种形式，是否要求 CI 校验命令存在？
6. LUMEN 是否按 P0 → P1 顺序另立治理 Sprint；本文不授权直接修改业务代码或引入工具依赖。

## 15. 最终建议

对一个由 AI 长期生成代码的项目，规范的目标不是让代码“看起来像一个人写的”，而是让关键决策不再依赖 AI 当时的随机选择：

- 质量原则决定优先级；
- 生命周期 Gate 决定什么时候可以继续；
- Profile、Concern 和 Adapter 决定这次加载什么；
- 项目基线与任务契约决定具体边界；
- 自动化工具决定哪些违规不能被带入主分支；
- 证据回流决定项目经验何时有资格成为模板规范。

LUMEN 已提供足够多的正反实例来形成第一版体系，但下一步最重要的不是继续增加文字，而是把最少的一组高风险规则变成真实 Gate：先保护测试数据库，再让 CI 运行代码检查，然后收敛错误、权限、事务和类型契约。只有规则、代码、测试与 CI 同时闭环，AI 编码的不确定性才会真正下降。
