# 需求探索模型（Requirements Exploration Model）

> 定位：正式 `00-03` 需求链路之前的探索 / 澄清模型，用于把“想法、反馈、痛点、体验问题”转成可回填的场景、用户需求、验收口径与阶段决策。
> 本文是 `docs/research/` 研究留痕，不替代 `docs/00-scenario.md`、`docs/01-user-requirements.md`、`docs/02-srs.md`、`docs/03-prd.md`；用户确认并回填后，才进入正式需求事实链。

## 0. 元信息

| 项 | 内容 |
|---|---|
| 日期 | 2026-07-11 |
| 适用项目 | LUMEN 团队知识库 Demo / MVP 演进 |
| 适用阶段 | 新需求发现、Phase2 范围细化、前端 P1 结构优化、客户访谈后需求整理 |
| 上游输入 | 用户反馈、实测记录、访谈纪要、产品愿景、竞品观察、Demo smoke 问题 |
| 下游输出 | 可回填到 `00/01/02/03/09` 的角色、场景、用户操作流、验收口径、REQ 候选与 Phase 建议 |
| 禁止用途 | 不直接授权实现；不绕过 `U-ID → REQ-ID → Phase → 设计 → Sprint → 测试 → 代码` 追溯链 |

## 1. 为什么补这个模型

当前项目已经有完整 `00-09` 文档链，但在两类场景里仍需要一个“前置探索层”：

1. **用户反馈较口语化**：例如“功能基本满足，但交互体验不太好，页面布局也不好”。这类反馈不能直接变成 REQ，需要先拆成观察、场景、痛点、用户目标和验收口径。
2. **Phase2 / P1 范围仍需细化**：`03-prd.md` 已确认 Phase2 核心 5 项，但每项还需要从用户使用路径、成功标准、非目标和风险边界上进一步收敛。
3. **避免功能清单驱动**：如果直接从“做标签、做反链、做 PDF”进入设计，容易缺少“谁在什么场景下为什么需要、怎样算好”的用户证据。

因此，本模型补齐的是：**输入材料 → 探索结论 → 正式需求回填**之间的转换层。

## 2. 四层模型

```text
原始输入 → 事实观察层 → 场景建模层 → 需求收敛层 → 正式回填层
```

| 层级 | 目标 | 产物 ID | 判断问题 | 下游回填 |
|---|---|---|---|---|
| 事实观察层 | 记录用户原话、实测现象、证据来源 | `OBS-ID` | 发生了什么？证据在哪里？ | `docs/inputs/`、`docs/research/` |
| 场景建模层 | 明确角色、触发条件、路径、上下文 | `R-ID` / `SC-ID` / `UFlow-ID` | 谁在什么时候为了什么做这件事？ | `00-scenario.md`、`01-user-requirements.md` |
| 需求收敛层 | 将痛点转成可验收的用户需求 | `NEED-ID` / `AC-DRAFT-ID` | 解决后用户可观察到什么变化？ | `01-user-requirements.md`、`09-verification.md` |
| 正式回填层 | 形成 REQ 候选、Phase 建议、非目标 | `REQ-CAND-ID` | 是否进入当前 Phase？是否需要设计 / 技术评估？ | `02-srs.md`、`03-prd.md`、`04-09` |

> 规则：探索 ID 不等于正式 U-ID / REQ-ID。只有经用户确认并回填后，才分配或更新正式 U-ID / REQ-ID。

## 3. 需求探索画布

每个新主题建议用一张画布收敛，不要一开始就写功能列表。

| 区块 | 需要回答 | 记录方式 | 示例 |
|---|---|---|---|
| 主题 | 这次探索要回答哪个决策问题？ | 一句话 | “前端 P1 是否需要 Tab / 路由？” |
| 来源 | 证据来自哪里？ | 用户原话、实测、截图、日志、访谈 | “用户操作一轮后反馈布局不好” |
| 角色 | 谁受影响最大？ | `R-ID` + 角色描述 | 新成员、知识维护者、管理员 |
| 场景 | 触发条件是什么？用户想完成什么？ | `SC-ID` + 触发 / 路径 / 结果 | 新成员搜索项目历史并追问来源 |
| 当前替代方案 | 现在用户如何绕过？ | 操作路径 / 人工补救 | 反复滚动右栏、复制摘要再回文档找上下文 |
| 痛点 | 阻塞、低效、误解还是风险？ | `OBS → Pain` | 结果不可点导致信息断裂 |
| 用户目标 | 用户真正想达成什么结果？ | Outcome 句式 | “不用离开当前任务即可定位来源文档” |
| 候选需求 | 可以怎么解决？ | `NEED-ID`，保持方案中立 | “检索结果应能回到来源内容” |
| 验收口径 | 用户怎样判断已解决？ | `AC-DRAFT-ID` | “点击结果标题后打开对应文档并保留来源提示” |
| 边界 | 不做什么？依赖什么？ | 非目标 / 风险 / 前置条件 | 不在 P0 做路由和响应式重构 |
| 优先级 | 为什么现在做或不做？ | 价值 × 证据 × 成本 × 风险 | P0 快赢、P1 另开设计 |
| 回填建议 | 影响哪些正式文档？ | U / REQ / Phase / TC 草案 | 01 用户需求、03 Phase、09 TC |

## 4. 推荐 ID 与字段

### 4.1 探索 ID

| ID | 含义 | 示例 |
|---|---|---|
| `EXP-YYYYMMDD-NN` | 一次探索主题 | `EXP-20260711-01` 前端体验优化 |
| `OBS-NN` | 事实观察 / 用户原话 / 实测证据 | `OBS-01` “页面布局不好” |
| `R-DRAFT-NN` | 候选角色 | `R-DRAFT-01` 新成员 |
| `SC-DRAFT-NN` | 候选场景 | `SC-DRAFT-01` 搜索后定位来源 |
| `UF-DRAFT-NN` | 候选用户操作流 | `UF-DRAFT-01` 搜索 → 查看摘要 → 打开文档 |
| `NEED-NN` | 候选用户需求，先不绑定实现 | `NEED-01` 检索结果可回到来源 |
| `AC-DRAFT-NN` | 候选验收口径 | `AC-DRAFT-01` 点击结果打开对应文档 |
| `REQ-CAND-NN` | 候选系统需求 | `REQ-CAND-01` 支持来源跳转 |

### 4.2 字段最小集

| 字段 | 必填 | 说明 |
|---|---|---|
| 来源 | 是 | 必须指向用户原话、文件、截图、日志或访谈记录 |
| 角色 | 是 | 至少一个受影响角色 |
| 场景 | 是 | 必须包含触发条件与目标结果 |
| 痛点 | 是 | 区分效率、理解、风险、审美、信任、成本 |
| 验收口径 | 是 | 用户可观察，不写内部实现 |
| 非目标 | 是 | 防止探索结论外溢成范围蔓延 |
| 回填目标 | 是 | 明确影响 `00/01/02/03/09` 哪些位置 |

## 5. 从反馈到需求的转换规则

### 5.1 句式转换

| 输入类型 | 不合格写法 | 合格转换 |
|---|---|---|
| 用户反馈 | “页面不好看” | “在搜索 / 问答任务中，用户需要减少无关面板干扰，以便聚焦当前任务” |
| 功能想法 | “加个 Tab” | “当用户只做搜索或问答时，需要一个聚焦视图，避免右栏多模块挤占阅读空间” |
| 技术方案 | “引入 react-router” | “用户需要稳定的视图切换与可分享位置；是否用路由需技术评估” |
| 缺陷现象 | “Markdown 原样显示” | “知识内容应按 Markdown 渲染，使标题、列表、强调可读” |
| 高层愿景 | “做智能知识库” | “新成员可通过带来源问答快速理解项目约束，且不能跨空间泄露” |

### 5.2 痛点分类

| 类型 | 判断标准 | 常见验证方式 |
|---|---|---|
| 效率痛点 | 操作步骤多、反复跳转、搜索成本高 | 任务耗时、点击数、用户复述 |
| 理解痛点 | 用户看不懂结果、上下文断裂 | 摘要理解测试、来源定位 |
| 信任痛点 | 答案无来源、权限不透明、AI 不可解释 | 来源显示、权限边界检查 |
| 风险痛点 | 误删、误恢复、越权、数据泄露 | 二次确认、权限测试、审计日志 |
| 信息架构痛点 | 功能堆叠、导航缺失、范围不清 | 页面路径图、卡片排序、任务聚焦测试 |
| 审美 / 质感痛点 | 文案、密度、视觉反馈影响可信度 | 人工 smoke、截图对比、可读性评估 |

## 6. 访谈 / 评审问题库

### 6.1 快速探索（15 分钟）

1. 你刚才想完成的任务是什么？
2. 哪一步最卡、最绕或最不确定？
3. 如果只能改一个点，哪个改完最有价值？
4. 你期望系统给出什么反馈，才算“我知道成功了”？
5. 哪些东西现在不要做，避免把范围做大？

### 6.2 深度探索（45-60 分钟）

| 维度 | 问题 |
|---|---|
| 角色 | 这件事主要是谁做？管理员、新成员、知识维护者还是普通读者？ |
| 频率 | 每天 / 每周 / 偶发？是核心工作流还是边缘场景？ |
| 触发 | 用户为什么开始这个动作？来自 onboarding、写作、检索、复盘还是交付？ |
| 输入 | 用户带着什么材料、问题或上下文进入？ |
| 输出 | 用户希望带走什么结果？文档、答案、链接、PDF、索引还是决策？ |
| 替代方案 | 没有系统时现在怎么做？用群聊、网盘、Notion、人工问人还是复制粘贴？ |
| 风险 | 做错会造成什么后果？越权、误删、误导、重复劳动还是交付延期？ |
| 验收 | 演示给你看时，哪三个动作通过就算能用？ |

## 7. 优先级评分

探索阶段只做轻量评分，目的是决定“进 P0 / P1 / Phase2 / 暂缓”，不是替代正式 PRD。

```text
Priority = 用户价值 × 证据强度 × 当前阶段适配度 ÷ 实现成本与风险
```

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 用户价值 | 偶尔改善体验 | 明显提升关键路径 | 直接影响核心闭环 / 付费价值 |
| 证据强度 | AI 推测 | 单次用户反馈或实测 | 多用户 / 多次实测 / 明确业务输入 |
| 阶段适配 | 超出当前 Phase | 与当前 Phase 部分相关 | 当前 Phase 必须收口 |
| 成本风险 | 需重构 / 新依赖 / 安全风险 | 中等改动 | 小改动、低风险 |

建议分级：

| 结果 | 处理 |
|---|---|
| 高价值 + 强证据 + 低成本 | P0 快赢，可直接形成小 PR，但仍需追溯依据 |
| 高价值 + 中高成本 | P1 / Phase 专项，先补设计确认 |
| 低证据 + 高成本 | 暂缓，补访谈或原型 |
| 高风险 | 先做 tech-env-eval / 安全评估 / ADR |

## 8. 回填门禁

### Gate A：探索是否足够

满足以下条件，才可从“想法”进入“候选需求”：

- 至少 1 条可追溯来源（用户原话、实测记录、输入文档或会议纪要）。
- 至少 1 个明确角色。
- 至少 1 个可复述场景。
- 至少 1 条用户可观察验收口径。
- 明确非目标与当前阶段边界。

### Gate B：是否回填正式需求

满足以下条件，才建议更新 `00-03`：

- 用户确认探索结论。
- 能映射到现有 U-ID / REQ-ID，或确需新增 U-ID / REQ-ID。
- 能说明 Phase 归属，不与 `03-prd.md` 现有路线图冲突。
- 有下游设计 / 验收影响说明。

### Gate C：是否进入设计 / 实现

满足以下条件，才可进入 `04-09` 或代码：

- `01` 有用户需求与验收口径。
- `02` 有系统需求规格。
- `03` 有 Phase / 优先级 / 非目标。
- 如涉及 UI，`docs/design/frontend-interaction.md` 或对应设计文档已覆盖。
- 如涉及新依赖、资源或平台能力，已完成 tech-env-eval 或 ADR。

## 12. 建议落地顺序

1. **短期**：用本文模型补做前端 P1 结构优化探索，确认是否引入导航 / Tab / 响应式 / 组件拆分。
2. **Phase2 主线**：对核心 5 项逐项跑探索画布，特别是 REQ-014、REQ-026、REQ-027。
3. **正式回填**：用户确认后，再把探索结论最小化回填到 `00/01/02/03/09`。
4. **再进入实现**：只有回填后的 U / REQ / Phase / TC 齐备，才进入设计与代码。

## 13. 风险与边界

| 风险 | 说明 | 防护 |
|---|---|---|
| 探索结论被误当正式需求 | `docs/research/` 是留痕，不是 00-03 权威事实 | 文首声明 + Gate B 回填门禁 |
| 功能清单继续膨胀 | 探索容易把所有想法都写进来 | 每项必须写非目标与阶段建议 |
| 用户反馈证据不足 | 单次反馈可能只是个体偏好 | 标注证据强度，低证据高成本项暂缓 |
| 方案先行 | 直接写 router / 组件库 / AI 方案 | 先写用户目标与验收，再评估实现方案 |
| 与 Phase 指针冲突 | 当前项目 Phase 指针仍需人工确认 | 只给 Phase 建议，不自动切指针 |
