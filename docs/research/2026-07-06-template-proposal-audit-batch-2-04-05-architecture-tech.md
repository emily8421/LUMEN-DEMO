## 2. 总体结论

`docs/04-architecture.md` 与 `docs/05-tech-spec.md` 已能支撑 Phase1 Demo 的基本设计：架构图、模块划分、关键流程、技术栈、资源约束与 Mock / 降级策略均已存在。但从模板复用角度看，04-05 仍需要更强的结构化规范，避免派生项目出现“架构图可读但边界不可审计”“技术栈清楚但依赖、配置、安全、风险验证不成体系”的问题。

结论：需要独立模板提案 P-02，建议文件名为 `_proposals/TEMPLATE-UPGRADE-04-05-architecture-tech-standard.md`。

## 3. `docs/04-architecture.md` 观察

### 3.1 已满足项

- 有系统架构图，能说明 React 前端、FastAPI、服务层、模型层、PostgreSQL + pgvector、文件解析、Embedding、LLM 的关系。
- 有子系统 / 模块划分，并为关键模块指向 `docs/design/*`。
- 有登录与空间切换、文档访问 / 搜索 / RAG 统一过滤等关键流程。
- 有 REQ / 功能 → 模块追溯矩阵。
- 与 `ai/project-rules.md` 的 Phase1 Demo 边界基本一致。

### 3.2 模板缺口

- 规范应更明确要求“架构目标与约束”，把 Phase、交付物形态、运行环境、项目形态裁剪和禁止项集中展示。
- 规范应区分“系统上下文图”和“容器 / 进程 / 组件视图”，避免一张架构图同时承担所有表达职责。
- 规范应要求组件 / 模块使用稳定 ID，例如 `COMP-001`、`MOD-001`，便于 05 / 06 / 07 / 08 / 09 追溯。
- 规范应要求关键流程含失败 / 降级路径，不只写成功路径。
- 规范应要求架构决策与取舍表，记录替代方案、影响范围和权威源，避免横切事实散落在 04 / 05 / project-rules。
- 规范应要求部署 / 运行拓扑将本机 Demo、服务器预案、端口、资源、Mock / 降级拆成可审计字段。

### 3.3 建议写入 P-02

- 将 `架构目标与约束` 设为 04 必备章节。
- 将 `系统上下文图`、`容器 / 进程 / 组件视图`、`模块划分` 拆清职责。
- 增加 `架构决策与取舍` 表，建议使用 `ADR-ID`。
- 增加 `Flow-ID` 关键流程模板，要求写成功结果、失败 / 降级路径、关联 REQ。
- 增加 `REQ → COMP / MOD / Flow` 追溯矩阵。

## 4. `docs/05-tech-spec.md` 观察

### 4.1 已满足项

- 有技术栈与版本表。
- 有关键技术决策，包括 pgvector、OpenAI 兼容接口、本机 Embedding、导入流水线、RAG、术语注入、鉴权、错误码和切块参数。
- 有 Phase 技术约束与编码约定。
- 有运行环境与资源评估，引用 `docs/env/local-env.md` 和项目资源软上限。
- 有 Mock / 降级策略：LLM 可 Mock 或远程 API，OCR 可降级为已提取文本。

### 4.2 模板缺口

- 规范应要求 `05` 独立列出依赖文件、配置文件、环境变量、密钥 / 凭据管理方式，避免技术方案只写“允许安装依赖”。
- 规范应要求引用技术环境评估报告的结论、已验证项、未验证项和补做时点；`collect-env` 不能替代评估。
- 规范应要求前端交互设计边界：何时需要 `docs/design/frontend-interaction.md`，技术方案只写工程约束，不替代页面流和验收路径。
- 规范应要求安全、隐私与合规考虑独立成章，尤其是真实数据、外部 AI、密钥、日志、权限与数据留存。
- 规范应要求技术风险与验证计划映射到 `docs/09-verification.md` 或技术评估报告，避免风险只停留在文字说明。
- 规范应要求技术栈状态枚举，区分 `已用`、`预留·未启用`、`候选`、`Mock`、`降级`、`禁止`。
- 规范应要求技术版本漂移处理：如果实现期选用不同版本，必须同步 05、依赖文件和验证记录。

### 4.3 建议写入 P-02

- 增加 `依赖与配置` 表。
- 增加 `技术环境评估结论` 子节，引用 `docs/research/*tech-env-evaluation*.md`。
- 增加 `前端交互设计边界` 子节。
- 增加 `安全、隐私与合规考虑` 表。
- 增加 `技术风险与验证计划` 表，使用 `RISK-ID` 并映射到 09 / Spike / PoC / Sprint。
- 增加技术状态枚举和版本漂移处理规则。

## 7. 提案拆分判断

本 Batch 建议只起草一个提案：

```text
_proposals/TEMPLATE-UPGRADE-04-05-architecture-tech-standard.md
```

原因：

- `04` 与 `05` 是总体设计的连续环节：04 定义“系统如何组织”，05 定义“用什么技术落地”。
- 两者共享环境约束、Mock / 降级、依赖、安全隐私和验证风险，拆分过细会重复。
- DB / API 契约应留到 P-03，详细设计统一结构应留到 P-06。
