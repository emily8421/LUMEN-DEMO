## 2. REQ-049 本地挂载文件可编辑（增删查改）

### 2.1 需求描述

当前本地挂载（REQ-018 模式 B，Phase2C）**只读**：左栏 LocalMountPane 可浏览 / 本地搜索 / 导入到 LUMEN，主区 LocalDocPreview 只读渲染。用户期望：**本地挂载的文件可在浏览器内编辑（增 / 删 / 改 / 查）**，即把「本地 vault」当可管理的工作目录用。

### 2.2 现状边界（已核实）

- `frontend/src/features/LocalDocPreview.tsx`：只读 ReactMarkdown 渲染，标注「本地·未入库·不上传服务端（不进 RAG）」，无编辑入口。
- `frontend/src/features/LocalMountPane.tsx`：仅「导入此篇 / 导入全部」按钮，无删除 / 新建 / 重命名。
- `frontend/src/app/useLocalVaultMount.ts` / `local-vault-fs.ts`：基于浏览器 File System Access API（`pickDirectory` / `readVaultFile` / `walkVault` / IndexedDB 存句柄），只有读路径，无 `createWritable` / `removeEntry` 写路径。
- 设计边界：Phase2C 硬天花板「仅本地挂载内容不上传服务端、不进团队 RAG」——**编辑是本地文件系统操作，不改变「不上传 / 不进 RAG」边界**，仅放开「只读」为「可本地读写」。

### 2.3 方案建议

- **后端零改动**：文件内容不落库，所有编辑走浏览器 File System Access 写句柄（`FileSystemWritableFileStream`）。
- **前端**：
  1. `local-vault-fs.ts` 补 `writeVaultFile`（`createWritable` + 覆盖写）、`createVaultFile`（`getFileHandle({ create: true })`）、`deleteVaultFile`（`removeEntry`）、`renameVaultFile`（`move()`）。
  2. `useLocalVaultMount` 补编辑态 state（`editingPath` / `editingText`）+ 对应 handler，保存后重建索引。
  3. `LocalDocPreview` 加「编辑」切换（复用 DocumentsFeature 的 textarea + 保存 / 取消）；`LocalMountPane` 加文件右键「重命名 / 删除」与目录「新建文件」。
  4. 编辑后本地倒排索引重建，搜索即时反映。
- **边界**：仅 Chromium（Chrome / Edge）经 http://localhost 可用（沿用现状）；写失败（权限吊销 / 句柄失效）走 needs-auth 重授权流程。

### 2.4 影响与验收

- 影响：REQ-018 模式 B 的「只读」→「本地可读写」；不涉及 DB / API / 团队 RAG；浏览器支持面不变。
- 验收：浏览器 smoke——新建本地文件 → 编辑保存 → 本地目录树与搜索反映；删除确认后文件消失；重命名生效；重扫（reindex）后一致。
- 是否立项：**待用户确认**。

## 3. REQ-050 成员管理配置成员可看哪些空间

### 3.1 需求描述

当前成员管理（REQ-047，`MembersFeature.tsx`）只管理**当前空间**成员：搜索邮箱添加 / 改空间角色 / 移除。用户期望：**成员管理视图里，除配置空间角色外，还能配置该成员可看哪些空间**（跨空间可见性）。

### 3.2 现状边界（已核实）

- `backend/service/space.py` `list_user_spaces`：用户可见空间 = 其 `lumen_space_members` 所在空间集合；`ensure_space_access` 拒绝非成员空间。
- `MembersFeature.tsx` 只对当前空间增删成员；无跨空间批量配置 UI。
- 全局 admin（`lumen_users.role=admin`）在用户管理页（`AdminUsersFeature`）可管理用户角色 / 禁用，但不管理用户与空间的关联。

### 3.3 方案建议

- **后端**：
  1. 新增「用户空间关联」查询：`GET /api/admin/users/{user_id}/spaces` 返回用户所属空间 + 各空间角色（admin 域，API 复用现有鉴权谓词）。
  2. 新增「批量授权」写接口：`PUT /api/admin/users/{user_id}/spaces`（body: 目标空间 + 角色清单；需覆盖全局 admin 鉴权 + 最后一个空间 admin 保护）。
  - 或复用 space 域成员接口循环调用（前端编排多个 `POST /api/spaces/{id}/members`），后端零新接口。**推荐后者（最小改动）**。
- **前端**：成员管理（或用户管理）每行加「空间可见性」展开区——列出该用户所属空间，勾选目标空间 + 角色；保存时逐空间调用现有成员 API。
- **边界**：不做「跨空间文档权限」细化；仅管理「成员可进入哪些空间」；空间内权限仍由空间角色决定。

### 3.4 影响与验收

- 影响：Sprint-28 空间成员模型不变，新增跨空间管理入口；全局 admin 才有管理权限。
- 验收：admin 给成员授予第二个空间 → 该成员空间切换下拉出现新空间 → 访问其文档 / 权限正确；撤销后立即不可见。
- 是否立项：**待用户确认**。

## 4. REQ-051 忘记密码 + 登录注册交互优化

### 4.1 需求描述

登录页（`App.tsx` 内联面板）需要：① 密码「小眼睛」显示/隐藏切换；② 忘记密码入口（重置密码能力）；③ 参考主流设计的注册 / 登录交互优化。

### 4.2 现状边界（已核实）

- 密码输入 `<input type="password">`，无可见性切换。
- **无忘记密码 / 重置密码能力**：Sprint-28 明确「移除用户 / 重置密码 / 邀请码」留候选；`backend/api/auth.py` 无 reset 端点；无邮件发送能力（demo 无 SMTP）。
- 注册 / 登录为内联 tab（`App.tsx:295-356`），非独立路由；无第三方 OAuth。

### 4.3 方案建议

- **前端（快）**：密码框加可见性 toggle（眼睛图标 + `type` 切换）；登录 / 注册交互细节优化（错误提示位置、按钮态、回车提交等）。
- **后端（忘记密码，需立项）**：
  1. 新增 `POST /api/auth/password-reset/request`（输入 email → 生成一次性 reset token，TTL 短、一次有效）。
  2. 新增 `POST /api/auth/password-reset/confirm`（reset token + 新密码 → 更新 `password_hash`）。
  3. 交付方式：demo 无 SMTP，token 交付可降级为「响应体返回 token + 提示运维人工下发」或接入邮件（需外部 SMTP / 中转，按 `project-rules §2.5` 资源约束评估）。
- **边界**：不做邮箱验证 / 自助找回邮箱；重置后旧 session 是否全部吊销待定（建议吊销，对齐跨设备安全）。

### 4.4 影响与验收

- 影响：新增 auth 端点 + `lumen_sessions` 联动；前端登录面板增强。
- 验收：请求重置 → 拿到 token → 确认重置 → 新密码登录成功；旧密码失败；token 过期 / 二次使用拒绝。
- 是否立项：**待用户确认**（前端小眼睛可并入批3，忘记密码后端独立）。

## 5. REQ-部署 · 开放团队使用（⑪）

### 5.1 现状

LUMEN 全栈本机运行：FastAPI 后端（`:18000`）+ Vite dev server 前端（`:5173`，绑 `::1`）+ PostgreSQL 16 / pgvector（`docker/compose.yml`，`lumen-pg` 容器，端口 `15432`）；Embedding 本机 `bge-small-zh`；LLM 走 OpenAI 兼容中转（`.env` 配置）。登录为真实账号体系（REQ-040..047）。

### 5.2 开放团队使用的部署建议（优先级排序）

| 方案 | 适用 | 改动 | 成本 | 建议 |
|---|---|---|---|---|
| **A. 公司内网服务器 + Docker 化部署** | 团队成员同一内网 | ① 后端 / 前端容器化（多阶段构建）；② 前端 `vite build` 产物由 FastAPI 静态托管或 Nginx 反代；③ PG 复用 compose；④ 前端绑 `0.0.0.0`（现绑 `::1`） | 低-中（一次容器化） | **推荐**——贴近现有架构，复用 docker/compose.yml，改动集中在部署脚本 |
| **B. 本机长期运行 + 内网穿透 / VPN** | 小团队临时验证 | 本机开端口 + frp / Tailscale / VPN 暴露 `18000/5173`；需处理绑定地址与鉴权 | 低（不改架构） | 过渡方案，不推荐长期（本机重启即失联，公网暴露有安全面） |
| **C. 云服务器（公司或公有云）** | 异地成员 / 正式试点 | 同 A 容器化 + HTTPS 域名 + 公网入口；需反向代理与 TLS | 中 | 正式试点的最终形态，但需先过数据外发 / 合规评估 |

### 5.3 关键决策点

1. **部署环境**：公司内网服务器（推荐）还是云？决定网络拓扑与合规要求。
2. **数据与外发**：真实团队文档是否入库？若会触发 AI 润色 / RAG 外发，需按 `project-rules §2.5` RG-008 口径明确接受；否则限制为仅本地挂载模式。
3. **LLM 通道**：服务器能否访问内网中转（`47.107.134.2:7777/v1`）？决定 `.env` 配置与降级策略。
4. **HTTPS**：内网部署可暂用 HTTP；公网必须 HTTPS（`cryptography` 证书或反代 TLS）。
5. **Embedding**：`bge-small-zh` 本机可跑（CPU），服务器需 4-8GB 内存余量；规模化后再评估内网 Embedding 服务。

### 5.4 建议下一步

- 若选方案 A：起一个 `docker/Dockerfile`（后端）+ 前端静态托管，或复用现有 `run-sprint16-demo.ps1` 改 `0.0.0.0` 绑定，写一份 `docs/env/deploy-guide.md` 部署手册。
- 是否立即实施：**待用户确认**（本批仅输出建议，不落部署代码）。
