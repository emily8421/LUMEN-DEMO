# LUMEN 大规模文档场景 · 分层信息架构与配色重评估

## 0. 问题重述

前几版原型（情报墙/星图/案卷夹）默认的文档规模是"一屏能摆下"的量级（几张到十几张卡片）。但你提出的是更真实的情况：

- 一个空间下有**多个文件夹**（对应不同项目/业务/主题）；
- 每个文件夹下可能有**几十到上百份文档**；
- 文件夹下还可能有**不限层级的子目录**。

这件事直接推翻了前三版的一个隐藏假设——"把关联可视化铺满整个屏幕就够用"。这个假设在文档量小时成立，量一旦上去就会失败，原因不是审美问题，而是**认知规律问题**：力导向关系图/星图这类"节点+连线"的可视化，人眼能有效辨认关联的节点数量大致在二三十个以内，超过这个数字，图会变成一团分不清方向的线（业内做知识图谱/网络分析可视化的产品，普遍都会在超过这个量级后做聚合或分页处理，而不是硬画全部节点）。所以量大之后，**不是换个好看的皮肤能解决的，需要换一套分层结构**。

同时你提出了两个明确要求，直接采纳，作为本次重评估的硬约束：
1. **分层次展示**：空间层 → 空间内的项目/主题层 → 子目录层（层级不限） → 文档层；
2. **文档层的阅读/编辑/预览用传统模式**，新颖交互是可选项而不是唯一路径，两者应该可以共存、可以切换，而不是二选一。

---

## 1. 核心原则：可视化只用在"有边界的集合"上

把此前三版的错误认知讲清楚，作为后续设计的第一原则：

> **图谱/星图/情报墙这类空间化可视化，适合"几十个节点以内、有明确边界的一个子集"，不适合"整个知识库的所有文档"。**

也就是说：这类可视化不应该是"知识库"的呈现方式，而应该是"**某个项目/某个主题下**"的呈现方式——因为只有在这个尺度下，节点数量才是可控的（一个真实项目下的核心文档，就算有几十上百份，真正"值得画出关联"的关键文档通常也就一二十份，其余是辅助材料，可以先折叠）。

这意味着信息架构要新增一层"**聚合视图**"，专门解决"文件夹/项目很多、文档很多"这件事，而不是指望空间层的一张图撑住一切。

---

## 2. 分层信息架构提案

```
Layer 0  空间层（Space）
   └─ Layer 1  空间总览（项目/主题聚合视图）——瓦片式，而非逐文档铺开
        └─ Layer 2  项目/主题内部（可能还有子目录）——同样先聚合，直到抵达"叶子文件夹"
             └─ Layer 3  叶子文件夹内的文档列表——默认传统模式（列表/表格）
                  └─ Layer 4  单篇文档——传统阅读器/编辑器（始终存在，不因导航方式而变化）
```

**关键设计决策**：Layer 1 和 Layer 2 展示的对象是"文件夹/项目/主题"这个粒度，**不是文档**；只有到了 Layer 3（叶子文件夹），才第一次看到具体文档列表，且默认用传统模式呈现；到了叶子层，如果这个文件夹内文档数量在可控范围内，才提供"以关系图查看"的**可选**按钮。

### 2.1 Layer 1：空间总览（聚合瓦片，替代"铺满屏幕的气泡/星星"）

不再让首页图谱试图画出空间里所有文档，而是**按文件夹/项目聚合成瓦片**，一个空间下即使有几十个项目，几十个瓦片也比几百个单独节点更可读：

```
┌───────────────────────────────────────────────────────────┐
│  brightlite-team                              [经典模式 ▾]  │
│                                                              │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐        │
│  │ 智慧园区照明  │ │ 客户沟通存档 │ │ 竞品与市场   │        │
│  │ 86 份文档     │ │ 23 份文档    │ │ 12 份文档    │        │
│  │ 3 处待核实冲突│ │ 今天更新     │ │ 上周更新     │        │
│  │ ▪▪▪▫▫ 活跃度  │ │ ▪▪▫▫▫ 活跃度 │ │ ▪▫▫▫▫ 活跃度 │        │
│  └──────────────┘ └──────────────┘ └──────────────┘        │
│  ┌──────────────┐ ┌──────────────┐                          │
│  │ 二期工程预研  │ │ 归档/其他    │   ...（更多瓦片）        │
│  │ 41 份文档     │ │ 9 份文档     │                          │
│  └──────────────┘ └──────────────┘                          │
└───────────────────────────────────────────────────────────┘
```

- 瓦片大小可映射"文档量"或"活跃度"，颜色深浅映射"最近更新的新鲜度"，冲突数量用一个小红点角标提示，而不是像情报墙那样把每一份文档的连线都画出来；
- 瓦片本身可以有一个极简的"迷你关系缩略图"（几个小点+几条线的图标级示意），暗示"这个项目内部结构复杂"，但只是一个图标，不需要认真渲染，点进去才认真画；
- 这一层的信息密度目标是"5秒扫一眼知道哪个项目最活跃、哪个项目有问题待处理"，不是"看清每份文档"。

### 2.2 Layer 2：项目内部（可能还有子目录）

点击"智慧园区照明"瓦片进入后，如果这个项目下还分了子目录（比如"接口方案""现场勘察""客户沟通""测试报告"），**再展示一层同样的聚合瓦片**，直到某一层不再有子目录、只有具体文档为止（即"叶子文件夹"）。层级深度不限，每多下钻一层，顶部面包屑就多一节：

```
brightlite-team ›  智慧园区照明  ›  接口与协议方案  ›  （已到叶子层，见 Layer 3）
```

面包屑始终常驻、可点击跳回任意上级，这是应对"层级不限"的关键——无论嵌套多深，用户永远知道自己在哪、能一键跳出去。

### 2.3 Layer 3：叶子文件夹——默认传统列表

到了真正装着文档的文件夹，**默认展示传统列表/表格**（这是你明确要求保留的部分）：

- 支持排序（按更新时间/名称/类型）、筛选（按标签/类型/状态）、搜索、分页或虚拟滚动（应对上百条数据）；
- 每行显示标题、类型、更新时间、冲突/待核实角标（如果有）；
- 这一层是"信息密度优先"的传统表格体验，不追求视觉新颖。

同时，在这一层提供一个**不强制、可关闭**的入口："以关系图查看"，规则见第4节。

### 2.4 Layer 4：单篇文档——传统阅读器/编辑器（不因导航路径而变化）

不管你是从传统列表点进来，还是从可选的关系图节点点进来，打开文档看到的都应该是**同一套传统阅读/编辑体验**（对照此前"印象笔记"文档里描述的富文本能力：标题分级、行内编辑、版本历史、AI润色、内部链接等）——这是唯一"必须一致"的部分，新颖交互只发生在"怎么找到这份文档"的过程中，不应该影响"打开之后怎么读/怎么写"。

## 3. 经典模式 与 探索模式：并存，而非二选一

按你的要求，"新颖交互体验可选"，具体做法是在合适的层级提供一个**模式切换器**，而不是让某一种可视化成为唯一入口：

| 层级 | 经典模式 | 探索模式（可选） |
|---|---|---|
| 空间总览（Layer 1） | 传统目录树列表（文件夹名+文档数，逐行展示，可展开折叠） | 聚合瓦片墙（如2.1所示） |
| 项目内部（Layer 2，若有子目录） | 同上，逐级目录树 | 同样的聚合瓦片，按子目录聚合 |
| 叶子文件夹（Layer 3） | 传统表格/列表（默认） | 关系图/情报墙（可选，见第4节的量级限制） |

- 顶部提供一个全局的"经典 / 探索"切换开关，**记住用户偏好**（整体默认值可设置，也允许逐层级用户临时切换查看一次）；
- 常驻一个可收起的**传统目录树侧栏**（贯穿所有层级都能唤出），不管当前停留在瓦片墙还是关系图，随时可以点开目录树直接跳转到任意文件夹/文档，作为"逃生舱"和"电梯"，这一点是对你需求的直接回应——**经典模式必须始终可达，不能被探索模式盖住**。

## 4. 视图自动降级规则（防止可视化在大量文档时失效）

这是解决"文档一多怎么办"的核心机制，建议做成产品的显性规则（可与团队讨论具体数字，这里给出经验性建议区间）：

| 该层级的节点/文档数量 | 默认视图 | 探索视图是否可用 |
|---|---|---|
| ≤ 25～30 | 探索视图（瓦片/关系图）可作为默认 | 完全可用，效果最佳 |
| 30～80 | 传统列表为默认 | 可用，但需要用户主动点击"以图谱查看"；打开后自动做**聚类简化**（次要节点合并为一个"其他 N 份"节点），避免铺满 |
| 80 以上 | 传统列表/表格（强制） | 关系图入口变为"先筛选后可视化"——引导用户先按标签/时间窗口/关键词缩小范围（比如"只看最近30天"或"只看含冲突的文档"），生成的是**局部**关系图，而不是尝试渲染全部 |

这样设计的好处：可视化能力不会因为数据量变大而"失效或变成噪点"，而是体面地**降级为更聚合的形式**，同时把决定权交给用户（"我知道东西多，我自己选要不要先筛一下再看图"）。

## 5. 配色与视觉语言重新评估

你的判断是对的——此前的"牛皮纸/图钉/回形针/手写体"这套视觉语言，本质上是在做一个"实体公告板"的怀旧模拟，**观感偏旧、偏怀旧手工感**，与"AI 情报分析工具"这个定位的科技感、专业感不太匹配，也不利于长期使用（信息密度高的分析场景下，纸张纹理和阴影反而增加视觉噪音）。这次全面换掉：

### 5.1 新配色方案

| 用途 | 旧方案的问题 | 新建议 |
|---|---|---|
| 背景 | 牛皮纸黄褐色 / 深空黑紫，两个极端 | 现代中性基底：浅色主题用近白灰 `#F6F7F9`，卡片用纯白 `#FFFFFF`，深色主题（可选）用石墨灰 `#14161C`，不用深空紫黑 |
| 文本 | 暖褐黑色（仿旧墨水） | 冷灰石墨色 `#1B1F27`，更干净、屏幕阅读更舒适 |
| 主品牌色 | 赭石/琥珀 `#A6532A`（像旧信封蜡封） | 现代靛蓝 `#4F46E5`（分析类工具常用的"专业科技感"色系，区别于此前三色系里已经用过的暖橙/冷青/深紫，也避免撞到 Claude 交互色 `#D97757`） |
| 冲突提示 | 暗红 `#B23A2E`（偏暗、偏土） | 清亮警示红 `#E5484D`，饱和度更高、辨识度更好 |
| 术语口径不一致 | 暗橙 `#C1812E` | 明快琥珀 `#F5A623`，与主品牌靛蓝形成清晰的冷暖对比而不冲突 |
| 同步/信息提示 | 灰蓝 `#3E6FA0` | 干净的信息蓝 `#2F80ED` |
| 连接线（关系图） | 手绘感牛皮纸绳索色 `#9C8A68` | 简洁的中性灰线 `#C7CCD6`，高亮时才转为主品牌靛蓝，不做"绳子/红线"的实体质感 |

### 5.2 字体重新选择

| 角色 | 旧方案 | 新建议 | 理由 |
|---|---|---|---|
| 标题/展示字体 | Source Serif 4（衬线，纸感） | 一款几何感现代无衬线（如 Space Grotesk / General Sans 类型） | 衬线体天然带"文档/纸张"的传统联想，换成几何无衬线更贴近"数据分析工具"的气质 |
| 正文 | Inter | 保留 Inter | 已是现代、可读性好的选择，无需更换 |
| 元数据/时间戳 | IBM Plex Mono | 保留（或换 JetBrains Mono，观感更"工程感"） | 等宽字体本身就是"数据/技术"的信号，保留 |
| 手写体批注（Caveat） | 用于"⚠矛盾"手写标签 | **去掉**，改用等宽/无衬线的清晰徽章（如小圆角标签+图标），不再模拟手写涂鸦 | 手写体是"复古怀旧"感最集中的来源之一，优先去除 |

### 5.3 视觉语言：从"实体公告板"到"数字原生的节点-连接"

- 卡片不再做"钉在墙上的纸片+图钉+轻微旋转"的物理模拟，改为**干净的圆角矩形卡片**，阴影克制、无纹理背景；
- 连接线不再是"手绘感的绳子"，改为**简洁的贝塞尔曲线细线**，默认灰色，命中高亮/冲突时才变色，线宽变化代替"手绘抖动"表达强调；
- 矛盾提示不再用"红色手绘警示线+手写批注"，改为**清晰的描边高亮 + 一个小型徽章图标**（比如卡片右上角一个圆形感叹号徽章，颜色用上面的警示红）；
- 术语高亮不再是"淡蓝色下划线模拟手写涂改"，改为统一的**虚线下划线 + 悬浮卡片**，卡片本身走干净的现代化 tooltip 样式（细阴影、圆角、无纸张纹理）；
- 整体气质目标：像一个现代的分析类 SaaS 工具（可参考同类产品里"专业但不冷冰冰"的调性），而不是"侦探剧证据墙"的实体模拟——**关系图/瓦片仍然保留"发现关联"的功能内核，但外观从"模拟真实物件"转向"数字原生的信息可视化"**。

## 6. 修订后的整体页面结构（结合分层与经典/探索双模式）

```
┌ 顶部：空间切换 · 面包屑（空间›项目›子目录…） · 经典/探索模式切换 · 搜索 ┐
│                                                                        │
│  经典模式：                          探索模式：                       │
│  ┌───────────┐┌─────────────────┐   ┌──────────────────────────┐     │
│  │目录树(可收│｜列表/表格        │   │ 聚合瓦片 或 局部关系图     │     │
│  │起，逃生舱)│｜（默认，Layer3） │   │（Layer1/2 聚合，Layer3    │     │
│  │           │｜                │   │ 可选、受第4节量级规则约束）│     │
│  └───────────┘└─────────────────┘   └──────────────────────────┘     │
│                                                                        │
│  点击任意文档 → 统一的传统阅读器/编辑器（Layer 4，两种模式殊途同归）   │
└────────────────────────────────────────────────────────────────────┘
```

- 经典模式下，左侧常驻目录树 + 右侧传统列表，是最保守、最不容易出错的默认体验，建议作为**新用户/新空间的默认开局模式**；
- 探索模式在 Layer 1/2 提供聚合瓦片，在 Layer 3 提供受限的关系图选项，**永远不强制**，且左侧目录树"逃生舱"在探索模式下依然可以呼出。

## 7. 待确认事项

- [ ] 第4节里"25-30 / 30-80 / 80+"的具体阈值只是经验建议，需要用真实空间的文档规律（比如一个典型项目通常沉淀多少份"核心文档"）来标定更准确的数字。
- [ ] 瓦片的"活跃度"指标具体怎么计算（更新频率？访问次数？待处理冲突数？）需要产品定义清楚，避免瓦片大小/颜色的含义模糊。
- [ ] "局部关系图"的筛选交互（按标签/时间窗口/关键词）具体UI尚未设计，建议单独出一版细化。
- [ ] 深色模式是否要作为正式选项对外提供，还是仅内部预留，需要产品确认。
- [ ] 新配色方案与此前"知识库Wiki/印象笔记/ima"三款参照产品的马卡龙/暖色调形成明显反差，这是刻意的差异化，但需要和团队确认这个"冷静分析工具"调性是否符合客户期望（不同客户对"工具感 vs 亲和感"的偏好可能不同）。
