## 2. 建议详情

### FC-01　office/wps → MD 转换范围与降级规则

**问题背景**：REQ-009 目前的口径是"仅 `.md`/`.txt`，条件通过"，真实 Word/PDF 解析是候选（RG-007，`python-docx`/`pdfplumber`，未接入）。用户希望在导入环节支持更常见的 office/wps 文档转 MD，但未明确具体格式范围和转换后的保真度预期。

**建议范围（按转换复杂度分级评估）**：

| 格式 | 建议 | 理由 |
|---|---|---|
| `.docx` | **纳入 v1** | `python-docx` 本来就是 RG-007 候选库，标题层级 / 加粗斜体 / 列表 / 图片 / 简单表格均可结构化提取映射为 MD 语法，边际成本低，可直接复用 REQ-009 已规划的技术选型 |
| `.xlsx` | **纳入 v1，但需明确降级规则** | 需新引入 `openpyxl`（或 `pandas`）。核心难点是表格结构如何塌陷为 MD：合并单元格、多 sheet、公式（只取计算值不取公式本身）、超大表格。建议规则：每个 sheet 转一个 MD 表格并以标题分隔；超过约 200 行自动截断并提示"完整数据请查看源文件"；公式一律取值 |
| `.pptx` | **本期不做** | `python-pptx` 技术上可提取文字，但 PPT 本质是视觉媒介，转 MD 信息损失最大（配图/排版/动画丢失，只剩孤立文字大纲），对知识库检索价值有限，建议留 P2 或愿景 |
| 旧版二进制 `.doc`/`.xls`/`.ppt`（97-2003） | **本期不做，明确拒绝并提示** | 无可靠纯 Python 库解析，需引入 LibreOffice headless 转码，增加容器依赖与运维成本；提示用户"请另存为 .docx/.xlsx 后重新上传" |
| WPS 私有格式 `.wps`/`.et`/`.dps` | **不单独适配** | WPS 现多默认另存为 office 兼容格式；若文件内容本身是 docx/xlsx 兼容格式，现有库大概率可读；读不了走"格式不支持"降级提示，不额外投入 |

**理由**：优先复用 REQ-009 已规划的技术选型（Word），Excel 单独评估表格降级规则后再纳入，避免为小众场景（PPT、旧格式、WPS 私有格式）引入 LibreOffice 这类重依赖。

**影响文档**：`02-srs`（新增 REQ-039）、`05-tech-spec`（新增依赖 openpyxl/pandas 及降级规则说明，纳入 RG 评估）、`08-dev-plan`（新 Sprint 任务，明确"不做 OCR、不做旧格式、不做 PPT"的禁止事项）

**建议阶段**：[P1.5]，建立在 REQ-009/RG-007 的文本抽取基础之上，但作为独立可验收项，不拖累 REQ-009 现有 Gate 节奏。

### FC-02　导入时"转 MD / 保留源格式"二选一，且保留源格式仍参与全文检索

**问题背景**：用户希望进知识库时可选择"转为 MD（主档）"或"保留源格式（仅兼容：存/读/查）"，但保留源格式的文档是否参与 AI 问答检索未明确。

**架构判断**：不管选哪种，要让 AI 问答检索到内容，都必须先把文档纯文本抽出来喂 Embedding——这一步本来就是 REQ-009/RG-007 的既定范围，和"是否生成可编辑 MD 文件"是两个不同粒度的工作，应拆成两层：

```
第一层（必做，REQ-009 范围）：纯文本抽取 → 喂 Embedding → 参与全文检索
第二层（可选，本次新增范围）：结构化转换（标题/列表/表格保留） → 生成可编辑 .md 文件
```

"保留源格式"只是不做第二层，第一层照样跑，边际成本主要在第二层（结构保真的 MD 生成），跟是否检索无关。若保留源格式的文档反而检索不到，会造成"为什么这份文档 AI 找不到"的体验落差。

**建议**：保留源格式的文档**参与全文 Embedding 检索**；文档预览区提示"该文档以源格式保存，如需在线编辑请手动转换为 MD"。

**影响文档**：`01-user-requirements`（新增 U-44，或作为 U-09 的阶段增量）、`02-srs`（REQ-039 内明确此 AC）、`04-architecture`（补充"纯文本抽取"与"结构化转换"两层管线设计）、`06-db-design`（`lumen_imports` 是否需要新增字段标记 `entry_format: md | original`，需与现有 `mime` 列对照评估）

**建议阶段**：[P1.5]，随 FC-01 一并纳入 REQ-039。

**问题背景**：REQ-027（单文档导出 PDF，受 RG-006 约束，待选型 weasyprint/reportlab）目前没有水印相关 AC。用户希望可选择加水印。

**影响文档**：`02-srs`（REQ-027 AC 增补）、`05-tech-spec`（RG-006 验证项增加水印能力检查）、`07-api-spec`（PDF 导出接口增加 `watermark` 可选参数）

### FC-04　格式转换独立工具（双向）

**问题背景**：URS 场景八 / 十三已提出"本地 MD 转 PDF"独立工具（上传 MD → 直接下载 PDF，不产生知识库条目，临时文件 24 小时清理），但目前只有骨架描述，无正式 REQ 号，且只覆盖单向。用户这次希望 office/wps → MD 也能脱离导入流程独立使用。

**建议**：将两个方向合并为一组独立工具需求（建议新开 REQ-040），因为产品形态一致（不产生知识库条目、临时存储、定时清理），可复用同一套上传-处理-下载-清理基础设施，不必分成两个 REQ：

- 方向一：上传 MD 文件 → 下载 PDF（可选水印，复用 FC-03 能力）
- 方向二：上传 office/wps 文件（范围同 FC-01）→ 下载转换后的 MD 文件
- 两个方向均不占用知识库导入/导出配额，不生成文档条目，处理产物本地临时存储不超过 24 小时后自动清理
- 入口位置：首页底部快捷栏（与 URS 场景十二"快捷按钮"设计一致）

**影响文档**：`01-user-requirements`（新增 U-45）、`02-srs`（新增 REQ-040）、`04-architecture`（独立工具的临时文件生命周期管理设计）、`06-db-design`（临时文件是否需要落库记录过期时间，还是纯文件系统 TTL）、`07-api-spec`（新增独立转换接口，明确不复用文档 CRUD 权限模型）

**建议阶段**：[P1.5B]，晚于 REQ-039（依赖同一套格式解析能力）、可与 REQ-027/FC-03 并行推进。
